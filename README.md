# Relay — 다른 사람의 GPU에서 내 LLM 실행

실행자가 다른 사람의 GPU를 선택하고, 자신이 실행할 GGUF 모델을 업로드하는 소규모 파일럿 서비스입니다. 제공자 PC가 업로드한 모델을 받아 적재하고 프롬프트를 실행합니다. 제공자가 미리 등록한 모델에 실행자를 묶지 않습니다. 웹의 기본 화면은 **LLM 실행**이며, 문서 추출은 기존 운영자 도구에 남아 있습니다.

## GPU를 빌려 내 모델 실행하기

1. **GPU에서 LLM 실행**을 누르고 개인 계정을 만들거나 복구 파일로 로그인합니다.
2. **다른 GPU 사용**에서 현재 연결되어 있고 새 모델 실행을 지원하는 GPU를 선택합니다.
3. 내 GGUF 모델을 업로드합니다. 단일 파일 20 GiB까지 지원하며 채팅 템플릿이 내장되어 있어야 합니다.
4. 문맥 길이를 지정하고 **GPU 빌리고 LLM 열기**를 누르면 대화 터미널이 바로 열립니다.
5. 모델 전송·적재가 끝나면 터미널에서 원하는 만큼 연속 대화합니다. **GPU 임대 종료**를 누르거나 제공자가 중지하면 모델이 GPU에서 내려갑니다.

대여 중에는 해당 GPU를 독점하고 모델을 제공자 PC에 유지합니다. 각 답변이 완료될 때 제공자 실행기가 보고한 새 입력 토큰과 출력 토큰 합계 1,000개당 1 CR을 올림해 정산합니다. 캐시에서 재사용한 입력 토큰은 보고된 경우 제외합니다. 요청 전에는 문맥 크기를 기준으로 최대 비용을 예약하고, 실제 비용과 차액은 답변 완료 후 자동 해제합니다. 실패·취소한 답변은 차감하지 않습니다. 정산액 10 CR당 1 CR을 서비스에, 나머지를 제공자에게 지급합니다. CR은 서비스 크레딧입니다. 업로드는 중앙 서버 디스크에 저장되며 제공자가 모델과 프롬프트를 받습니다. GGUF 외 모델 형식·사용자 코드·임의 컨테이너는 실행하지 않습니다. 실제 GPU 메모리 적합성과 모델 호환성은 적재할 때 확인합니다. 제공자 PC가 보고한 사용량을 신뢰하는 파일럿이며 서버가 원격 GPU의 연산량을 독립 검증하지는 못합니다.

지속 대여에는 제공자 프로그램 0.5.0 이상이 필요합니다. 노트북에 **모델 업로드 실행 미지원** 또는 **PC 도우미 업데이트 필요**가 보이면 노트북에서 현재 서버의 PC 도우미 ZIP 전체를 새 폴더에 풀고 다시 참여하세요. 연결 대기·중지 상태는 별도로 표시됩니다. 분산 실행 공간은 아래의 별도 실행 그룹과 선택적 예비 그룹을 사용합니다.

GPU 제공자는 웹 **내 GPU 제공**에서 10분짜리 연결 코드를 만들고, PC 도우미에서 **GPU만 제공 (실행자의 모델 사용)**과 로컬 llama-server를 선택한 뒤 코드를 입력해 **서버에 바로 연결**을 누릅니다. 도우미가 실행기를 검사해 서버에 직접 등록하므로 확인 JSON과 수동 연결 파일 전달이 필요하지 않습니다. 실제 제공은 PC 도우미의 **검사하고 참여 시작**을 눌러야 시작합니다. 기존 JSON 방식은 호환용으로 남아 있습니다.

새 모델 임대 경로의 검증 범위는 [실행자 모델 업로드 검증 기록](docs/reports/renter-model-validation-ko.md)에 정리합니다.

전체 구성도와 KV·인증·저장·복구 경계는 [전체 구성 아키텍처](docs/architecture-review-ko.md), 코드 구조와 수정 지점은 [프로젝트 구조·LLM 리팩토링 가이드](PROJECT_MAP.md)를 확인하세요. 운영 안내·전달 지침·과거 검증 기록은 [문서 목차](docs/README.md)에서 찾을 수 있습니다.

AWS 사이트에 다른 컴퓨터의 GPU를 연결해 검증하려면 [AWS 실제 GPU 실행·검증 Codex 지침서](docs/handoffs/AWS-REMOTE-GPU-CODEX.md) 한 파일을 해당 컴퓨터에 전달하세요. 공개 다운로드, 개인 계정 등록, 실제 모델 실행, GPU 계측·회수와 보고서 작성까지 포함합니다. 이전 임시 서버 방식은 [두 컴퓨터 GPU·VRAM 검수 기록](docs/reports/remote-vram-test-ko.md)에 남겨 두었습니다.

## 여러 GPU의 VRAM으로 하나의 모델 실행

웹의 **분산 LLM**에서 GPU 후보의 비용과 성능 선언을 보고 전용 실행 공간을 만듭니다. 기본은 실행 그룹 하나이며 예비 그룹은 선택 사항입니다. 공간마다 활성 요청은 하나이고 `/v1/workspaces/<id>/chat/completions`라는 고정 주소를 유지합니다. 생성 때 한 번 받는 공간 전용 키와 연결 설정 JSON을 저장해 채팅 앱·에이전트에 연결합니다. 일반 `/v1/chat/completions`는 같은 모델의 미예약 그룹 중 빈 슬롯을 찾아 세션 KV·준비 상태·빈/만료 캐시·점유율에 따라 배정합니다.

기존 코드를 **실행 공간 → 자원 구성 → 모델 실행 → GPU 제공·회수**의 네 책임으로 연결했습니다. 한 호스트에서 모델이 실행되면 RPC 없이 이용하고, 원격 GPU가 필요하면 llama.cpp의 연속 레이어 분할과 장치별 KV를 사용합니다. 예비를 선택한 공간만 장애 시 같은 전체 대화 기록으로 한 번 재생성하며, 예비가 없으면 자동 우회하지 않습니다. 선택한 그룹의 비용만 합산합니다. 분산 시간제 자동 과금은 아직 없으며 미측정 속도를 계산해 표시하지 않습니다.

[Petals 비교·아키텍처 결정](docs/petals-architecture-decision-ko.md)에 따라 EC2 웹·인증·정산·SQLite와 기존 GGUF 실행기를 유지합니다. 필수 예비 예약을 없앴지만 기존 예비 프로세스를 자동 중지하지 않으며, tokens/s 향상을 실측한 변경은 아닙니다.

[라우팅·KV 코드 검토](docs/reports/routing-kv-review-ko.md)를 반영해 모델별 세션을 구분하고, 잘못된 입력이나 문맥 초과로 기존 KV를 지우지 않도록 입력 검사 순서를 바꿨습니다. 같은 그룹의 동시 준비 검사는 공유합니다.

공간 정보·주소·키 해시는 SQLite에 저장하지만 대화·진행 요청·KV는 저장하지 않습니다. 공간 종료는 예약과 KV를 해제하고, 실제 GPU 반환은 분산 실행기의 중단 버튼(`--gui`) 또는 Ctrl+C로 소유 프로세스를 종료합니다. SSE는 기본적으로 완료 후 전달하며, 즉시 스트리밍 클라이언트는 `restart_on_failure:true`의 응답 폐기·재시작·완료 신호를 처리해야 합니다.

[네 계층 계약·복구 API](docs/distributed-workspace-design-ko.md), [분산 실행 설정·운영](docs/distributed-inference-ko.md), [그룹 설정 예제](docs/examples/inference.config.json)를 확인하세요. `RELAY_INFERENCE_CONFIG`로 구성하며 선택할 그룹의 모델 적재와 필요한 사설 연결은 운영자가 준비합니다. 단일 호스트 또는 LAN·인증된 사설 overlay WAN의 신뢰된 제공자가 대상입니다. 실제 다중 GPU·WAN 성능과 예비 복구 목표는 아직 실장비로 검증하지 않았습니다. EC2 배포 구성은 유지하며 이번 소스 변경을 운영 서버에 자동 배포하지 않습니다.

배포된 AWS 서버는 **https://gpu-together.3.38.50.72.sslip.io**입니다. `OPEN-AWS-RELAY.cmd`를 열면 로컬 서버 실행 없이 접속합니다. 관리자 키는 기존 `.relay/admin-key.txt`를 사용합니다.

## 버튼으로 시작하기

Windows에서는 실행 파일을 더블 클릭하고 웹 화면의 시작 안내를 따라갑니다. 사전 빌드 ZIP에는 화면이 포함되어 있어 `npm install`이나 빌드 명령이 필요하지 않습니다. 처음 한 번은 Node.js 22.13 이상을 설치해야 합니다. Node.js 자체를 자동 설치하는 패키지는 아직 제공하지 않습니다. Node.js가 없으면 실행기가 설치 안내를 표시합니다. 소스 폴더에서 실행해 화면 빌드가 없으면 의존성 설치와 빌드를 자동으로 진행하므로 최초 실행에 인터넷 연결과 준비 시간이 필요합니다.

1. ZIP을 원하는 폴더에 풀고 `START-RELAY.cmd`를 더블 클릭합니다.
2. 중앙 서버가 시작되면 브라우저가 열립니다. 기본 로컬 실행에서는 2분 동안 유효한 일회용 로그인으로 콘솔에 접속합니다. 원격 공개 주소나 보안 쿠키를 설정한 환경에서는 관리자 키로 로그인합니다.
3. 시작 안내에서 체험 또는 실제 GPU 연결을 선택합니다.
4. 먼저 체험할 경우 예제 문서를 불러오고 실행 버튼을 누릅니다. 작업 진행과 결과는 화면에서 확인합니다.

체험은 규칙 기반 fixture입니다. LLM을 실행하거나 GPU 성능을 측정하지 않습니다. 체험과 실제 실행의 계정·원장·모델·작업은 분리됩니다.

서버 실행 창은 서버가 동작하는 동안 유지해야 합니다. 창을 닫으면 중앙 서버가 종료됩니다. 브라우저가 열리지 않으면 `http://127.0.0.1:8788`로 접속하고 `.relay/admin-key.txt`의 관리자 키로 로그인할 수 있습니다. 관리자 키와 SQLite DB는 `.relay` 아래에 생성되며 배포 ZIP에 포함되지 않습니다. 검증에 사용한 환경은 Windows / Node.js 22.17.0이며 Node.js SQLite 실험 기능 경고가 출력될 수 있습니다.

## 문서별 독립 추론은 어디에서 실행하는가

| 위치 | 실행하는 기능 | 필요한 것 |
|---|---|---|
| 지정한 중앙 서버 1대 | 웹 화면 제공, 관리자 인증, 작업 배정, lease·기한 만료 정리, 원문 근거 검사, 결정적 병합, 예산·정산·상태 저장 | Node.js, 영속 디스크, 원격 연결 시 TLS |
| 참여자 개별 컴퓨터 | 등록한 모델을 적재하고 배정받은 문서를 추론, 결과 제출, 소유한 추론 프로세스 회수 | Python, 고정 llama.cpp 실행파일, GGUF, chat template, 해당 모델을 실행할 자원 |
| 개인 브라우저 | 자기 GPU 제공·일시 중지, 잔액·수익 확인, 다른 GPU 이용, 자기 결과 조회 | 개인 계정 복구 파일 |
| 운영자 브라우저 | 서비스·보안 관리, 노드 차단, 전체 원장 점검, 추가 토큰 배정 | 관리자 세션 |

중앙 서버에 GPU나 외부 LLM API 키는 필요하지 않습니다. 문서 원문과 결과는 중앙 서버에 저장되고, 배정된 문서는 해당 참여자에게 전달됩니다. 중앙 서버는 LLM 추론을 수행하지 않습니다. 원문 근거 검사와 최종 병합은 일반 코드로 수행합니다.

참여자는 중앙 서버로 outbound HTTPS 요청을 보냅니다. 참여자 PC의 포트를 인터넷에 열지 않습니다. 제공자는 작업을 요청하고, 중앙 서버가 모델·문맥·VRAM·허용 노드를 확인해 배정합니다. 브라우저는 상태를 조회하며 스케줄링 타이머를 실행하지 않습니다.

서버의 유지보수 루프는 기본 1초 간격으로 만료된 lease와 작업 기한을 정리하고 체험을 진행합니다. 브라우저와 제공자가 모두 끊겨도 서버가 살아 있으면 기한 경과에 따른 예약 해제가 진행됩니다. 서버를 재시작하면 저장된 상태에서 만료 처리를 재개합니다. 서버가 꺼져 있는 동안에는 새 배정·정산을 할 수 없습니다.

## 실제 GPU 연결

Python 3.10 이상, 로컬 GGUF, 등록할 llama.cpp server 빌드, 모델에 맞는 UTF-8 chat template 파일이 필요합니다. 런타임과 모델은 자동 다운로드하지 않습니다. 한 PC에서의 실제 GPU 실행 확인 결과는 아래 검증 기록에 정리했습니다.

### 개인 계정으로 GPU 제공·이용하기

**내 GPU·토큰**에서 개인 계정을 만들고 계정 복구 파일을 저장합니다. 기본 가입 토큰은 100 CR이며 GPU 제공 수익이 같은 계정에 쌓입니다. 내 GPU, 사용 가능·예약 토큰, 기여 수익, 이용 내역을 확인하고 다른 사람의 GPU에 작업을 요청할 수 있습니다.

**내 GPU 연결하기**에서 일회용 연결 코드를 만들고 PC 도우미에 입력하면 관리자 승인 없이 GPU를 등록합니다. 확인 파일 업로드와 연결 파일 다운로드는 필요하지 않습니다. 실제 GPU 실행은 PC 도우미의 **검사하고 참여 시작**, 종료는 **참여 중지**로 제어합니다. 여러 PC의 수익이 한 계정으로 모이며 다른 사람의 잔액이나 작업을 조작할 수 없습니다.

현재 요금은 문서 정보 추출 1개당 10 CR(제공자 9, 서비스 1)입니다. 작업 요청 시 예약하고 결과 확정 시 정산합니다. [개인 계정·GPU 제공·토큰 이용 절차](docs/participant-onboarding-ko.md)를 확인하세요.

### 운영자가 모델과 PC를 직접 등록하기

1. 웹 콘솔의 시작 안내에서 참여자 프로그램을 내려받고 참여자 PC에 압축을 풉니다. Windows에서 `START-PROVIDER.cmd`를 더블 클릭하면 설정 창이 열립니다. Python과 Tkinter가 설치되어 있어야 합니다.
2. 설정 창이 Windows·WSL의 저장된 모델을 자동 탐색합니다. 목록에서 GGUF를 골라 **이 모델 선택**을 누르면 모델 경로와 내장 채팅 템플릿이 준비됩니다. 기본 위치 밖에 저장했다면 **폴더 추가**를 누릅니다. llama-server도 자동으로 찾아 목록에 표시합니다. 하나만 발견되면 자동 입력되고, 여러 개면 사용할 실행기를 목록에서 선택합니다. 내장 템플릿이 없는 모델은 해당 템플릿을 직접 선택합니다. 필요하면 고급 설정에서 문맥 길이를 확인하고 **파일 검사** 후 **모델 검증 파일 저장**을 누릅니다. 파일의 SHA-256은 프로그램이 계산하며 기본 파일명은 `relay-model-contract.json`입니다. **다음: 연결 설정**을 누르면 모델 준비 창에서 별도의 연결 설정 창으로 이동합니다.
3. 운영자는 웹 콘솔에서 모델 계약 JSON을 불러오고 이름·필요 VRAM을 확인해 모델을 승인합니다. 문맥 길이와 VRAM 요구량은 실제 장비에서 확인한 값을 사용합니다.
4. 웹 콘솔에서 해당 모델의 PC를 등록하고 **연결 설정 저장**을 누릅니다. 파일명은 `relay-provider-<PC ID>.json`이며 PC 이름도 담습니다. 다른 PC가 참여한다면 해당 PC로 파일을 전달합니다.
5. 도우미의 **2단계 연결 설정** 창이 다운로드 폴더의 연결 파일을 자동으로 찾습니다. 첫 설정에서 하나를 찾으면 불러오고, 여러 개라면 서비스 주소와 PC 이름을 보고 선택합니다. **검사하고 참여 시작**을 누르면 참여를 시작합니다. 주소·노드 ID·인증키를 터미널에 입력할 필요가 없습니다. 중지는 같은 창의 **참여 중지** 버튼으로 실행합니다.
6. 웹 콘솔에서 자동으로 갱신되는 연결 상태를 확인하고 실제 작업을 제출합니다. 연결 전에는 대기 상태이며 체험 성공만으로 실제 GPU 연결이 완료되지는 않습니다.

처음에는 연결 파일이 없어도 됩니다. 개인 계정으로 웹의 **내 GPU 연결하기**에서 **계정 복구 파일 저장 → GPU 등록 → 연결 설정 저장** 순서로 진행합니다. GPU를 등록하는 것만으로 연결파일이 다운로드되지는 않습니다. 모델 검증 JSON은 모델 확인용, 계정 복구 JSON은 로그인용, 연결 설정 JSON은 PC 도우미 연결용입니다.
참여자 ZIP(`relay-pc-setup.zip`)의 `START-PROVIDER.cmd`는 PC 설정 창을 열며 중앙 웹 서버를 시작하지 않습니다. ZIP 미리보기 안에서 실행하지 말고 **모두 압축 풀기** 후 생성된 폴더에서 실행하세요. `provider` 폴더를 포함한 모든 파일이 필요합니다. 실행 오류가 나면 CMD 창에 오류를 표시하고 대기합니다. 자동 업데이트 버전을 처음 한 번 설치하면, 이후 같은 CMD를 실행할 때 GitHub의 최신 정식 버전과 비교하고 SHA-256 검증 후 업데이트합니다. 이전 CMD에는 이 기능이 없어 처음 한 번 교체가 필요합니다. 자세한 배포 절차는 [참여자 자동 업데이트](docs/provider-auto-update-ko.md)를 참고하세요. 스케줄링 서버가 꺼져 있으면 운영자가 서버를 실행해야 합니다. 참여자 PC에서 `START-RELAY.cmd`를 실행할 필요는 없습니다.

웹에서 받는 도우미 ZIP에는 해당 서비스의 주소가 포함되어 **웹 설정 열기**가 같은 사이트를 엽니다. 자동 업데이트를 거쳐도 이 주소는 유지됩니다. 연결 파일 자동 찾기는 배포되는 동일한 도우미 ZIP에 포함됩니다. Windows는 시스템의 다운로드 폴더(위치를 옮긴 폴더 포함), macOS는 Downloads, Linux는 설정된 다운로드 폴더를 확인합니다. 브라우저가 다른 폴더에 저장한다면 **연결 폴더 선택**으로 위치를 지정하거나 기존 **연결 파일 불러오기**를 사용합니다. 예전 `relay-provider-private.json` 파일도 인식합니다.

도우미를 켜 둔 상태에서 새 연결 파일을 저장해도 자동으로 찾습니다. **연결 다시 찾기**는 검색 중 표시와 완료 후 연결 개수·검색 폴더를 보여 줍니다. 이미 불러온 연결 파일은 다운로드 폴더 밖에 있거나 이름을 바꿔 저장했어도 재검색 목록에 표시됩니다. 현재 불러온 파일의 전체 경로도 연결 안내에 표시합니다. 이미 저장하거나 선택한 연결과 실행 중인 연결은 새 파일로 자동 교체하지 않습니다. 파일을 찾거나 불러오는 것만으로 GPU 실행을 시작하지 않으며 **검사하고 참여 시작**을 눌러야 합니다.

자동 탐색은 Hugging Face·LM Studio·Ollama의 기본 캐시, 환경변수로 지정한 캐시, 일반적인 프로젝트의 models 폴더와 WSL 배포판의 모델 위치를 제한된 범위에서 확인합니다. 디스크 전체를 탐색하지 않으므로 사용자 지정 위치는 **폴더 추가**로 지정합니다. 모델 이름·형식·용량·누락 파일을 표시하고, Transformers 모델은 현재 GGUF 실행기에서 바로 사용할 수 없다고 안내합니다. 검색 및 선택 과정에서는 모델 다운로드·변환·추론을 시작하지 않습니다. GGUF 내장 템플릿은 원본을 수정하지 않고 사용자 설정 폴더의 templates 하위에 저장합니다. 형식 확인은 전체 파일 무결성이나 GPU 실행 가능성의 검증을 대신하지 않습니다.

llama-server 검색은 PATH, 일반 설치 위치, 다운로드와 프로젝트 폴더를 제한된 범위에서 확인합니다. Windows에서는 도우미·사용자 홈·시스템 드라이브의 바로 아래 프로젝트에 있는 `.relay/runtimes`와 `.relay/runtime`도 확인하므로, 다운로드한 도우미와 서버 프로젝트가 다른 폴더에 있어도 Relay 런타임을 찾습니다. 임의의 하위 폴더 전체를 탐색하지 않으므로 더 깊거나 다른 드라이브에 저장했다면 **검색 폴더 추가**로 지정합니다. 찾지 못하면 설치 ZIP을 모두 풀고 **다시 찾기**를 누를 수 있습니다. 실행기 파일을 검색하거나 선택하는 과정에서는 프로그램을 실행하지 않습니다. 실제 모델과의 호환성은 파일 검사와 참여 시작 단계에서 확인합니다.

다음 실행에는 이전에 선택한 파일과 연결 파일·추가 검색 폴더 경로를 복원합니다. **검사하고 참여 시작**을 눌러야 실행되며 자동으로 GPU를 점유하지 않습니다. 연결 키는 별도 환경설정에 복사하지 않고 이전에 내려받은 연결 파일에서 읽습니다. 파일을 옮기거나 삭제했다면 다시 선택하세요.

모델 및 llama-server는 신뢰하는 출처에서 준비하고 라이선스를 확인해야 합니다. 등록한 계약과 동일한 실행파일·모델·템플릿으로 실행합니다. 브라우저만으로 로컬 모델이나 GPU 프로그램을 실행할 수 없으므로 참여자 프로그램이 필요합니다.

연결 파일에는 해당 노드의 인증키가 들어 있습니다. 해당 참여자에게만 전달하고 공개 저장소나 채팅방에 올리지 마세요. 키를 분실하면 기존 노드의 키를 폐기하고 다시 등록합니다.

동일 컴퓨터 실험에서는 기본 주소 `http://127.0.0.1:8788`을 사용할 수 있습니다. **이 주소가 담긴 연결 파일은 다른 PC에서 사용할 수 없습니다.** 다른 PC를 연결하려면 운영자가 중앙 서버의 HTTPS 주소를 먼저 구성해야 합니다. 사설 IP를 HTTP로 지정하는 원격 연결은 지원하지 않습니다. TLS·DNS·방화벽 설정을 자동 처리하는 설치 프로그램은 아직 포함되어 있지 않습니다.

고정 llama.cpp 빌드는 `/v1/chat/completions/input_tokens`, `/props`, JSON response schema를 지원해야 합니다. 어댑터는 문맥을 초과한 입력을 잘라 실행하지 않고 실패 처리합니다.

제공자는 지정한 전용 llama-server 프로세스를 직접 시작합니다. 기본 로컬 포트는 8081이며, 이미 사용 중이면 연결을 거부합니다. SIGINT/SIGTERM, lease 갱신 실패, 원격 회수 시 자신이 시작한 프로세스를 종료합니다. 회수 상태에서는 모델을 다시 적재하지 않습니다. 실제 GPU 메모리 반환 시간은 장비·드라이버에서 측정해야 합니다.

### 고급: 명령줄 실행

Windows 이외의 중앙 서버는 프로젝트 루트에서 `node standalone/server.mjs`로 실행하고 브라우저에서 관리자 키로 로그인합니다. Python/Tkinter를 사용할 수 있는 다른 환경에서는 `python3 provider/setup_gui.py`로 설정 창을 열 수 있습니다. GUI 없이 참여자를 실행하려는 경우 아래 명령을 사용할 수 있습니다.

```sh
python provider/provider.py --server /path/llama-server --model /path/model.gguf --template /path/chat-template.jinja --print-contract
```

출력의 `modelDigest`는 GGUF 해시, `runtime`은 실행파일 해시, `template`은 템플릿 해시입니다. 웹의 개인 계정에서 이 계약으로 모델과 PC를 등록한 뒤 다음과 같이 실행합니다. 아래는 Linux 셸 예시입니다.

```sh
export RELAY_NODE_TOKEN='발급받은 제공자 키'
python provider/provider.py --server /path/llama-server --model /path/model.gguf --template /path/chat-template.jinja --context 8192 --coordinator https://relay.example.org --pool local-owner --node 발급된-노드-ID
```

`https://relay.example.org`는 운영자가 구성한 중앙 서버 주소로 바꿉니다. `--pool local-owner`는 현재 단일 풀의 고정 식별자입니다.

## 중앙 서버를 다른 컴퓨터에서 접근하기

AWS에서 상시 실행하려면 [AWS 서울 리전 배포 안내](docs/aws-deployment-ko.md)를 참고하세요. `npm run package:server`로 기존 작업 데이터·키를 제외한 서버 ZIP을 만들고, EC2 한 대에서 Docker Compose + Caddy로 HTTPS·자동 재시작·영속 볼륨을 구성합니다. 도메인이 없으면 `gpu-together.<Elastic IP>.sslip.io`를 테스트 주소로 사용할 수 있습니다. 이 구성은 중앙 서버용이며 참여자의 GPU 추론은 각 PC에서 계속 실행합니다.

기본 서버는 `127.0.0.1:8788`에만 바인딩합니다. 원격 제공자와 브라우저를 연결하려면 지정 서버에 TLS reverse proxy를 구성하고, HTTPS 주소를 이 로컬 서버로 전달합니다. 프록시는 연결 수·요청 크기 제한도 적용해야 합니다.

Windows PowerShell에서 같은 서버의 TLS 프록시를 사용하는 예시입니다.

```powershell
$env:RELAY_PUBLIC_ORIGIN = 'https://relay.example.org'
$env:RELAY_SECURE_COOKIE = '1'
node standalone/server.mjs
```

브라우저도 동일한 `https://relay.example.org`로 접속합니다. 이 예시는 프록시·인증서를 설치하거나 DNS를 생성하지 않습니다. 원격 TLS 구성과 WAN 운영은 별도 검증이 필요합니다. 프록시가 다른 호스트에 있을 때만 `RELAY_HOST`를 적절한 사설 인터페이스로 설정하고 방화벽으로 프록시 접근을 제한합니다.

| 환경 변수 | 기본값 / 역할 |
|---|---|
| `RELAY_HOST` | `127.0.0.1`; 중앙 서버 바인딩 주소 |
| `RELAY_PORT` | `8788`; 중앙 서버 포트 |
| `RELAY_DATA_DIR` | 프로젝트의 `.relay`; 관리자 키와 SQLite 데이터 위치 |
| `RELAY_ADMIN_TOKEN` | 미지정 시 파일에서 읽거나 생성; 직접 지정 시 32자 이상 |
| `RELAY_PUBLIC_ORIGIN` | 원격 웹 콘솔의 HTTPS origin; 경로·후행 슬래시 없이 지정 |
| `RELAY_SECURE_COOKIE` | HTTPS 운영에서는 `1`; 관리자 쿠키에 Secure 적용 |
| `RELAY_TRUST_PROXY` | 기본 비활성; 제공된 AWS 프록시 구성에서만 `1`. 프록시가 단일 `X-Real-IP`를 덮어쓰고 서버 포트를 외부에 노출하지 않아야 함 |
| `RELAY_SIGNUP_CREDITS` | `100`; 개인 계정 최초 가입 시 1회 지급하는 CR, 0~1000 |
| `RELAY_MAINTENANCE_MS` | `1000`; 서버 유지보수 간격, 250~60000ms |

중앙 서버와 데이터는 운영자가 소유합니다. 현재 단일 서버이므로 장애 시 가용성을 보장하지 않습니다. 백업은 서버를 정상 종료한 뒤 `.relay` 전체를 안전한 위치에 복사하는 방식부터 시작할 수 있습니다. 관리자 키가 포함되므로 접근을 제한하세요. 자동 백업·복원 검증과 고가용성 구성은 아직 포함되지 않습니다.

## 보안과 권한

현재 범위는 **개인 계정·GPU 소유권·CR 잔액 + 운영자 관리 콘솔 + 단일 풀**입니다. 개인은 복구 파일로 로그인하고 직접 GPU를 등록·제공하거나 자기 잔액으로 다른 GPU의 작업을 이용합니다. 운영자는 서비스와 보안을 관리합니다. 이메일·실명 기반의 중복 가입 판별과 여러 풀은 구현하지 않았습니다. PC 연결 키는 계정 복구 키와 별개이며 해당 노드의 실행 프로토콜에만 사용합니다.

추론 프로세스에는 제공자 인증키와 클라우드 키를 전달하지 않습니다. 최소 환경 변수만 넘기며 HTTP redirect를 거부합니다. 문서 URL은 출처로 저장할 뿐 서버가 URL에 접속하지 않습니다. 임의 셸·코드·도구 실행은 지원하지 않습니다.

TLS와 파일 해시는 제공자 호스트로부터 문서 내용을 숨기거나 원격 계산의 진위를 증명하지 않습니다. 공개·비민감 데이터만 제공자에게 맡기는 신뢰 모델입니다.

## 실행과 정산 계약

- 한 문서는 독립적인 논리 task이며 기술적 실행 시도는 최초 실행을 포함해 최대 3회입니다.
- lease는 30초, 한 시도의 hard stop은 180초입니다. 서버 시각과 epoch를 사용합니다.
- 노드당 활성 lease는 1개입니다. 공급이 없으면 대기하며 작은 모델로 교체하지 않습니다.
- 제공자마다 등록한 모델 계약 하나를 고정합니다. 모델·문맥·VRAM·허용 노드 조건과 작업 간 순환 배정을 사용합니다.
- 실행 완료 비용은 문서당 10 CR이며 제공자 9 CR, 운영 1 CR입니다. 자가보고 토큰은 과금에 사용하지 않습니다.
- 최초 보조금 1,000 CR은 별도 발행 기록입니다. 제공자의 기여 잔액은 새 작업의 결제 계정으로 선택해 재사용할 수 있습니다.
- 계정별 가용 잔액과 작업 예산을 함께 검사합니다. 기술적 재시도는 예약을 재사용합니다.
- 결과 품질과 실행 정산을 분리합니다. 의미적 오답이나 인용 검사 실패가 있어도 약정된 실행 완료 요금은 지급됩니다.
- 품질 재호출은 새 task와 새 10 CR 예약이며 동일한 작업 예산에 포함됩니다.
- 같은 결과의 중복 제출은 기존 영수증을 반환합니다. 과거 lease, 다른 노드, 모델 계약 불일치는 거절합니다.
- API 생성 요청의 `requestId`는 최근 24시간·512개 범위에서 멱등 처리합니다. 정산 멱등성은 task 영수증으로 계속 유지합니다.
- 취소·실패·기한 경과의 미사용 예약은 해제하고 이미 확정된 지급은 유지합니다.
- 최종 종합은 검증된 필드의 결정적 병합입니다. 별도 LLM 요약을 실행하지 않습니다.

## 저장 구조와 파일럿 상한

결과·원장·lease·예산을 SQLite의 같은 풀 상태에 저장하고 revision 조건부 갱신(CAS)으로 한 번에 확정합니다. API와 서버 유지보수 루프가 동일한 코어를 사용하며, 충돌 시 최신 상태와 시각으로 최대 10회 재시도합니다. SQLite는 WAL 모드로 실행합니다.

현재 상한은 노드 20개, 등록 모델 8개, 미보관 작업 24개, 작업당 문서 4개, 문서당 4,000 UTF-16 문자, 추출 필드 6개, 작업별 누적 task 16개, 풀 상태 약 1.7MB입니다. 진행 중 결과마다 64KB 여유를 예약합니다. 상태 한도에 가까워지면 새 작업을 거절하고 결과 내보내기·보관을 안내합니다. 보관은 원문·출력 내용을 제거하고 정산·결과 해시는 보존합니다.

이 상한은 파일럿의 처리량·저장량을 통제하는 애플리케이션 정책입니다. 완료 이력과 원장은 무한 확장하지 않습니다. 장기 운영에서는 관계형 테이블과 보관 저장소 분리, 백업·복원, 사용자별 권한, 정밀 계측이 필요합니다. 자동 모델 전환, 소유자 PC의 유휴 상태 감지, 시간표에 따른 자동 참여, 실화폐 결제는 포함하지 않습니다.

## 개발과 재빌드

```sh
npm ci
npm run dev
```

개발 명령 하나로 중앙 서버 8788과 Vite 화면 5173을 실행합니다. `http://127.0.0.1:5173`에서 같은 관리자 키로 로그인합니다. 개발 화면의 `/api`와 `/v1`은 중앙 서버로 전달됩니다. 개발 서버는 로컬 개발용입니다.

```sh
npm run build
npm start
```

빌드는 `standalone-dist`를 생성합니다. `npm start`는 빌드된 화면과 API를 중앙 서버 8788에서 함께 제공합니다. `npm run build:standalone`과 `npm run start:standalone`도 같은 명령의 별칭으로 유지합니다. 별도의 플랫폼 프로젝트, 호스팅 계정, D1 마이그레이션은 필요하지 않습니다.

## 재현 가능한 검증

```sh
npm test
python -m unittest discover -s tests -p "*_test.py" -v
npm run check
npm run lint
npm run build
```

- 코어: 복구, 오래된 실행 거절, 취소, 예산 경쟁, 중복 정산 방지, 기여 재사용, 원문 인용, 상태 재시작.
- 서버 유지보수: 브라우저 없이 lease·기한 만료, 체험 진행, 제공자 결과와의 동시 정산, 유휴 상태 쓰기 방지, 재시작 복구, 종료 시 진행 중 처리 정리.
- HTTP: 실제 Node/SQLite 서버의 인증·CSRF·제공자 권한·동시 정산·영속 복구.
- 설정 실행기: 일회용 로그인 만료·재사용·외부 요청 차단, 서버 주소 확인, 제공자 ZIP 무결성, 자동 준비 및 종료.
- PC 설정 도우미: 연결 파일 검증, 자동 해시, 모델 불일치, 비밀키 전달·로그 제외, 소유한 자식 프로세스 종료.
- Python 제공자: 구조화 요청, 문맥 상한, 파일 해시, 모델 불일치, 프로세스 회수, redirect 거절, 환경 격리, 회수 상태 유지.
- 장애 회귀: 긴 체험 문서·잘못된 입력·갱신 형식, 잘못된 JSON/SSE와 준비 단계 취소를 `npm test`에 포함합니다. Python 전체 검사에는 연결 종료/불완전 응답·남은 lease와 독립 마감 감시 검사가 포함됩니다.
- 브라우저: Playwright와 Chrome이 준비된 환경에서 `npm run test:browser`로 빌드 후 실행합니다. 저장 직후 응답 유실, 동일 폼 재시도의 단일 정산, 새/수정된 제출 구분, PC 등록 키 복구를 검사합니다. 별도 설치의 Playwright는 `RELAY_AUDIT_PLAYWRIGHT`에 `index.mjs` 절대 경로를 지정할 수 있습니다.

[심층 검증 당시 발견사항](docs/reports/service-validation-ko.md)과 [장애 수정·재검증 결과](docs/reports/service-validation-fixes-ko.md)를 함께 확인하세요. 같은 열린 폼의 재시도 ID와 PC 키는 메모리에 유지하며, 페이지 새로고침이나 로그아웃을 넘는 브라우저 복구는 보장하지 않습니다.

자동 HTTP·제공자 테스트의 추론 응답은 synthetic fixture입니다. 아래의 로컬 GPU 한 건 검증과 별개로, 일반적인 추론 품질·다양한 장비의 메모리 회수·전력·WAN 장애율·p50/p95·비용 우위·3대 이상 실GPU 종단 간 실행·스케줄러의 성능 우위는 입증하지 않았습니다. 기획서의 “20% 개선”, “95% 성공”을 실측 성과로 주장하지 않습니다.

### 로컬 GPU 실행 확인 (2026-09-18)

공식 llama.cpp b10964 Windows CUDA 12.4 빌드와 CUDA DLL의 SHA-256을 검증한 뒤 RTX 3050 Ti 4GB에서 기존 Qwen3-4B Instruct Q3_K_M 모델을 문맥 8192로 실행했습니다. Relay 실제 작업 1건이 완료됐고 제품명·메모리 추출 및 원문 근거 검증을 통과했습니다. 설정 도우미의 작업 프로세스를 거쳐 실행했으며, 중지 후 GPU 메모리 반환을 확인했습니다. 이 PC의 짧은 예제 검증으로, 다수 장비·장시간 부하·원격 연결의 성능이나 안정성까지 검증한 결과는 아닙니다.

## 참여자 프로그램 자동 업데이트

처음 한 번 [GitHub 참여자 배포 ZIP](https://github.com/wellseekogi/gpu_combine/releases/latest/download/relay-provider.zip)을 모두 압축 해제하고 `START-PROVIDER.cmd`를 실행합니다. 이후에는 같은 실행기가 최신 정식 버전을 비교하고, ZIP과 포함 파일의 SHA-256 검증 후 새 버전을 실행합니다. 공개 저장소이므로 GitHub 로그인은 필요하지 않습니다. 기존 모델·연결 파일·설정은 유지합니다.

실행 중인 참여 작업은 자동으로 중단하지 않습니다. 새 버전은 설정 창을 닫고 다시 실행할 때 적용됩니다. 네트워크나 업데이트 검증에 문제가 있으면 검증된 기존 버전을 사용합니다. 개발 소스에서 직접 실행할 때는 편집 중인 로컬 코드를 사용합니다.

배포자는 `provider/version.json`의 버전을 올리고 같은 버전의 `provider-v` 태그를 push하면 됩니다. 테스트·패키징·GitHub Release 게시는 자동으로 진행됩니다. [설치·검증·배포 절차](docs/provider-auto-update-ko.md)를 참고하세요.
