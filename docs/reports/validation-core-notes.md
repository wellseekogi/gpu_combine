# 문서 처리 코어 독립 검증 결과

> 수정 전 발견 기록입니다. 후속 수정과 현재 상태는 [수정·재검증 결과](service-validation-fixes-ko.md)를 참고하세요.

검증일: 2026-09-18. 범위: `lib/relay/engine.mjs`, `lib/relay/service.mjs`, `standalone/maintenance.mjs` 및 기존 테스트의 계약. 기존 서비스 코드는 수정하지 않았다. 실제 `.relay` 데이터·키·GPU·외부 서비스에는 접근하지 않았고, 독립 테스트는 메모리 저장소와 가상 시계만 사용한다.

## 실행 결과

```sh
node --test tests/audit-core.test.mjs
```

6개 테스트 중 2개 통과, 4개 실패. 실패 테스트는 안전한 기대 동작을 명시한 회귀 테스트이므로 현재 코드에서 실패하는 것이 감사 결과다. `package.json`의 기존 `npm test` 목록에는 이 파일을 추가하지 않았다. 따라서 기존 테스트 전체 통과가 아래 4개 문제의 해결을 의미하지 않는다.

## 재현된 결함

### C1. 유효한 긴 체험 문서가 같은 풀의 정상 작업까지 최종 실패시킨다 — P2

- 근거: `engine.mjs:78`의 fixture가 원문 한 줄 전체를 값과 인용에 각각 복사한다. `engine.mjs:83`은 결과를 12,000 UTF-8 바이트로 제한한다. `engine.mjs:145`은 문서를 4,000 UTF-16 문자까지 허용한다. `engine.mjs:128`의 전체 task 반복 중 한 submit 예외가 발생하면 `service.mjs:23`에서 중단되어 `service.mjs:30`의 CAS에 도달하지 않는다. 유지보수의 예외 격리 단위는 task가 아니라 pool이다(`maintenance.mjs:53`, `:68`).
- 재현: 문서 `license: ` + `가`.repeat(3991)를 만들면 정확히 4,000 UTF-16 문자로 create가 성공한다. 같은 풀에 `license: MIT` 한 줄의 정상 작업도 만든다. 두 작업을 배정한 다음 7초에 유지보수를 실행하면 긴 문서의 생성 결과가 상한을 넘겨 전체 변경이 버려진다.
- 장기 관찰: 30초 lease 만료와 재배정을 3회 가상 진행하면 정상 문서도 작업 상태 `partial`, task 상태 `failed`, attempts 3으로 끝난다. 유지보수 오류 3회 모두 `결과 크기 제한을 초과했습니다.`였다. 정상 문서의 결과가 매번 먼저 생성되어도 최종 저장은 취소된다.
- 영향: UI에서 허용하는 체험 문서 하나가 무관한 체험 작업의 진행과 정산을 막는다. live GPU 경로의 동일한 장애를 주장하는 결과는 아니다.
- 통과 기준: 모든 허용 demo 문서를 처리 가능한 fixture로 만들거나, 문제 문서만 명시적인 실패로 종료한다. 같은 풀의 정상 문서는 완료되어야 하고 잘못된 문서가 다른 작업의 재시도 횟수를 소모해서는 안 된다.

### C2. 잘못된 허용 노드 타입이 전체 노드 허용으로 바뀐다 — P2

- 근거: `engine.mjs:153`의 `Array.isArray(p.allowedNodes) ? p.allowedNodes : []`.
- 재현: `allowedNodes: "demo-2"`를 전달하면 요청이 수락되고 저장된 allowlist는 `[]`다. tick 후 실제 배정 노드는 `demo-0`이었다.
- 영향: 관리자/API 클라이언트가 명시한 배정 제한이 형식 오류 때문에 조용히 제거된다. 정상 UI가 보내는 배열 입력에서는 재현되지 않는다.
- 통과 기준: 속성 생략과 명시적인 빈 배열만 전체 노드 허용으로 해석한다. 지정한 값이 배열이 아니면 상태를 변경하지 않고 400을 반환한다.

### C3. 불완전한 lease 갱신 요청이 새 실행 권한을 발급한다 — P2

- 근거: `engine.mjs:114`가 속성 유무 또는 구조 검증 대신 `if(p.attemptId)`로 갱신과 신규 배정을 구분한다. 거짓 값이면 `engine.mjs:119`에서 claim한다. `PROJECT_MAP.md`는 갱신 요청과 신규 배정 요청의 구분 계약을 유지하도록 명시한다.
- 재현: epoch 1의 lease가 만료된 후 `poll`에 올바른 모델 계약과 `attemptId: "", epoch: 1`을 보낸다. 요청은 거절되지 않고 epoch 2의 새 lease를 반환한다. attempts는 2가 된다.
- 영향: 잘못 구성된 heartbeat가 의도치 않게 재배정·재시도 횟수를 소모한다. 인증된 동일 제공자의 프로토콜 오류이며, 다른 제공자의 권한을 얻거나 기존 결과로 이중 정산하는 문제로 확인된 것은 아니다.
- 통과 기준: `attemptId` 또는 `epoch` 중 하나라도 지정되면 둘 다 올바른 형식이어야 한다. 잘못되거나 오래된 갱신은 400/409로 거절하고 신규 배정을 수행하지 않는다.

### C4. null 문서가 입력 오류 대신 저장소 장애로 분류된다 — P2

- 근거: `engine.mjs:144`는 문서 배열의 원소 타입을 검사하지 않고 `engine.mjs:145`에서 `d.text`를 읽는다. `service.mjs:37`은 알려지지 않은 예외를 일괄 503으로 변환한다. `server.mjs:117`도 이 오류 응답을 사용한다.
- 재현: 정상 create 요청에서 `documents: [null]`로 바꾸면 `TypeError: Cannot read properties of null (reading 'text')`가 발생하고 실제 `errorResponse()`의 상태는 503이다.
- 영향: 잘못된 클라이언트 입력이 저장소 장애로 표시되어 사용자에게 잘못된 복구 안내를 하고, 클라이언트의 503 재시도를 유도할 수 있다. 확인된 저장 상태 손상은 없다.
- 통과 기준: 문서 원소가 null/배열/비객체인 경우 400을 반환하고 저장 상태는 동일하게 유지한다.

## 추가 통과한 경계

1. 유효한 결과에 잘못된 usage(`total_tokens: -1`)를 붙이면 400을 반환하며 저장된 시도 상태·결과·잔액·원장은 변경되지 않았다. engine 함수 내부의 일시 변경이 있더라도 service CAS 전에 실패하므로 부분 정산은 저장되지 않는다.
2. lease를 20초 간격으로 갱신해도 만료 시각은 최초 실행의 180초 hard stop을 넘지 않았다. 정확히 180초인 시각에 기존 갱신과 결과 제출은 모두 409로 거절되고 요청자 잔액은 1,000 CR로 유지되었다.

기존 테스트에는 정상 정산 원자성, 중복 제출 CAS, 계정별 예약, 소유자 회수, 노드별 1슬롯, 오래된 epoch 결과 거절, 품질 재호출 예산, 원장 보존, 보관 후 중복 정산 방지, SQLite 재시작 등이 있다. 본 독립 검사에서는 전체 기존 suite를 중복 실행하지 않았다.

## 정상 동작의 최소 판정 기준

| 영역 | 판정 기준 |
|---|---|
| 입력 경계 | 모든 API 입력의 타입·길이·상호 의존 필드를 확인하고, 잘못된 값은 4xx이며 상태를 변경하지 않는다. 명시한 제한을 형식 오류 때문에 완화하지 않는다. |
| 정산 | 계정 합계=발행량, 계정별 가용액>=0, task당 정산 1회, 완료 결과·지급·예약 해제 동시 확정, usage 값은 정액 요금을 바꾸지 않는다. |
| 실행 권한 | node+attemptId+epoch+서버 시각 일치, 갱신/신규 배정 분리, lease 30초와 hard stop 180초 준수, 만료·회수 결과 거절. |
| 실패 격리 | 문서 하나의 처리 오류가 무관한 정상 작업을 실패시키지 않는다. 재시도는 유한하며 최종 종료 시 미사용 예약이 반환된다. |
| 동시성·재시작 | revision 충돌 시 최신 상태와 시간을 재확인한다. 결과 재전송/관리자 재전송이 두 번 정산·생성되지 않는다. 저장된 상태로 재시작해도 만료·영수증 계약을 유지한다. |
| 품질 | 원문 인용의 존재와 UTF-16 위치를 확인한다. 의미적 정답 보장은 별도 사람 검토 대상이며 인용 존재 검사 통과와 동일하지 않다. |

모든 검증은 합성 문서와 메모리 저장소 기반이며 실제 GPU 모델 출력, 원격 PC 중단, 물리 네트워크 장애, 운영 DB 백업·복원, 장기간 용량 고갈 실측을 대신하지 않는다.
