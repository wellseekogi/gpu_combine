# CUDA 잔차·RMS 커널 최적화 검증 — 2026-09-29 1차

이 문서는 1차의 고정 128스레드 측정 기록이다. 이후 작은 행 분기·20W 전력 조건·설치된 실제 모델 조사는 [2차 보고서](kernel-round2-2026-09-29-ko.md)에 구분했다.

독립 CUDA 커널을 실제 RTX 3050 Ti Laptop GPU에서 개선했다. 같은 실행 안의 이전 융합 커널보다 1/33/128/257행에서 각각 **6.10% / 16.01% / 5.59% / 2.60%** 짧은 시간을 기록했다. **llama.cpp 실행 그래프에는 아직 연결하지 않았고 전체 모델·두 PC 통신 속도 향상을 측정한 결과가 아니다.**

## 구현과 유지한 계약

- 폭 4,096인 연속 F32 입력, F32 가중치와 두 출력(잔차 합·정규화 결과)을 유지한다. Q8_0 모델과 f16 KV 캐시 정밀도는 바꾸지 않았다.
- `float4`로 16바이트씩 읽고 쓰며, 합산값을 레지스터에 보관해 정규화에 재사용한다. 네 개의 독립 F32 제곱합을 warp shuffle로 축약한다.
- 기본 블록을 1,024스레드에서 128스레드로 줄였다. 공유 메모리는 128→16바이트/블록, 드라이버가 보고한 레지스터는 24→56개/스레드다. 스레드 수를 곱한 블록당 레지스터 수는 24,576→7,168개이며 실제 할당 단위·occupancy는 하드웨어에 따른다. 로컬 메모리 spill은 두 구현 모두 0바이트다.
- 모든 버퍼는 서로 겹치지 않아야 하고 최소 16바이트 정렬이어야 한다. 호스트가 컴파일 때 사용한 `RMS_THREADS`와 같은 스레드 수로 행당 블록 하나를 실행해야 한다.
- `__fadd_rn`으로 잔차 덧셈의 F32 반올림을 보존한다. FMA·fast math·flush-to-zero를 켜지 않았다.

잔차 합은 CPU의 F32 반올림 결과와 **비트 단위로 동일**하다. 정규화는 축약 순서가 달라 이전 구현과 비트 동일하지 않다. 모든 원소에 기존 기준 `abs(error) ≤ 2e-6 + 2e-6 × abs(CPU double)`를 적용했고 기본 검사 최대 절대 오차는 `9.88e-7`이었다. 기존 융합 커널과 2회 실행 참조의 본문은 그대로 보존했으며, 둘 사이의 비트 동일성도 계속 검사한다.

## 측정 방법과 수치

NVIDIA 드라이버 592.27(API 13010), 기존 작업 폴더의 NVRTC 12.4, Windows WDDM 환경이다. 운영체제 설정·드라이버·GPU 클록·전력 제한을 변경하지 않았다. 자체 소유 CUDA context, stream, 메모리, 이벤트와 그래프만 생성·해제했다. 종료 뒤 `nvidia-smi`의 사용량은 다시 0MiB였다.

각 그래프에 200회의 연산과 시작·종료 이벤트 노드 2개를 넣었다. 후보/이전 융합은 202개, 2회 실행 참조는 402개 노드인지 검사한다. 이벤트를 그래프 안에서 기록하여 Python 실행 요청 사이의 공백을 측정 구간에서 제거했다. 각 변형을 최소 150ms 예열하고 순서를 고정 seed로 섞어 15회 재생한 중앙값을 사용한다. 마지막 그래프 출력도 직접 실행에서 검사한 출력과 비교한다.

| 행 수 | 이전 융합 µs | 새 융합 µs | 시간 감소 | 2회 실행 참조 µs | 참조 대비 감소 |
|---:|---:|---:|---:|---:|---:|
| 1 | 2.263 | 2.125 | 6.10% | 2.924 | 27.32% |
| 33 | 8.315 | 6.984 | 16.01% | 9.774 | 28.55% |
| 128 | 48.691 | 45.967 | 5.59% | 61.809 | 25.63% |
| 257 | 95.872 | 93.377 | 2.60% | 120.765 | 22.68% |

2회 실행 참조는 이 저장소의 작은 ADD→RMS×weight 커널이며 컴파일된 llama.cpp baseline이 아니다. 캐시가 따뜻한 합성 버퍼를 반복 사용하고 그래프 스케줄링 시간이 포함된다. 노트북 클록은 자동 조절되므로 독립 실행끼리의 작은 차이를 확정적인 개선으로 해석하면 안 된다. 257행의 작은 개선폭은 메모리 대역폭이 주된 제한이라는 해석과 일치하지만, DRAM 트랜잭션 하드웨어 카운터로 확인한 것은 아니다.

32/64/128/256/512/1024스레드 vector 변형, 128/256/512/1024스레드 scalar 변형, vector 제곱합 의존성 완화까지 비교했다. 128스레드는 주 대상인 prefill의 128/257행에서 유리했다. 512스레드는 작은 1/33행에서 더 빨랐으므로 `--threads`를 남겼다. 단일 장비의 결과로 자동 분기 규칙을 운영 실행기에 추가하지 않았다. 전체 보정 결과·원시 샘플·소스 및 PTX 해시는 [검증 JSON](../research/kernel-performance-20260929.json)에 있다.

## 메모리 수치의 범위

검사 프로그램은 후보·참조의 출력 버퍼를 순차 재사용한다. 257행에서 명시적 GPU 할당이 25,280,512→**16,860,160바이트(16.08MiB)**로 감소했다. 새 값에는 출력 양쪽의 256바이트 guard 총 1KiB가 포함된다. 약 **33.31% 절감은 검사 프로그램의 비교용 할당에 한정**되며 모델 VRAM 절감이 아니다.

실제 융합 연산의 다섯 버퍼 크기는 이전 융합 연산과 같다. 그래프의 다음 소비자가 잔차 합을 필요로 하므로 두 출력 중 하나를 제거하거나 입력에 덮어쓰지 않았다. context/JIT/그래프 관리 메모리는 명시적 데이터 버퍼 합계에 포함되지 않는다. 양자화·KV 압축을 통해 수치나 캐시 용량을 바꾸지 않았다.

## 재현과 경계 검사

```powershell
python scripts/check-cuda-kernel.py --self-check
python scripts/check-cuda-kernel.py --nvrtc work/kernel-development/nvrtc/nvidia/cuda_nvrtc/bin/nvrtc64_120_0.dll --threads 128 --rows 1 33 128 257 --repeats 200 --samples 15 --output work/performance-20260929/kernel-final.json
python scripts/check-cuda-kernel.py --nvrtc work/kernel-development/nvrtc/nvidia/cuda_nvrtc/bin/nvrtc64_120_0.dll --rows 1 2 17 31 32 33 127 128 129 257 1024 --repeats 0
```

기본 9개 GPU 사례는 무작위 1/33/128/257행, 영벡터, 상쇄, 작은 값, 큰 동적 범위, F32 반올림 경계를 포함한다. 별도 경계 검사는 1..1024행의 11개 크기와 위 5개 패턴으로 16개 사례다. epsilon `1.4e-45`, `1e-12`, `1e-4`, `3e38`마다 7개 사례도 통과했다. 출력 전체를 NaN으로 채워 빠뜨린 쓰기를 확인하고, 범위 밖 쓰기를 감시하는 guard를 검사한다. 잘못된 행/열/스레드 수, 0·음수·비유한·F32 underflow/overflow epsilon, 비정렬·겹친 버퍼는 GPU 실행 전에 거절한다.

최종 커널 SHA-256은 `04b0ba2bcf5c22aec333a47e9d60b6745fb399f046b7b29290c5f6a533a50591`다. 실험 전 원본은 `df7376ee1fe35183bddfe4c26f71f1611d572f3090a442b1f268a44111d8a868`로 보관했다. NVRTC의 compute_75·compute_86 컴파일을 확인했으며 **실제 실행은 compute_86만** 검증했다.

## 운영 연결에 필요한 검증

현재 llama.cpp는 이미 RMSNorm→곱셈과 일부 decode MatVec→ADD를 융합한다. 이 후보를 연결하려면 고정된 upstream 소스의 실제 그래프 소비 관계, 버퍼 생존 기간·정렬, 기존 융합 선택 규칙을 함께 검증해야 한다. 전체 소스·빌드 체인과 비교 모델 실행이 없는 상태에서 DLL을 바꾸거나 우회 로더를 추가하지 않았다. GTX 1660 SUPER 실제 실행, 모델 logits 오차, prefill/decode 전체 지연, 두 PC 동시 실행이 남아 있다.

GPUDirect나 NIC→GPU 직접 DMA는 구현하지 않았다. CUDA 커널의 GPU 직접 실행과 네트워크 DMA는 별도 기능이며 이 결과가 원격 통신의 zero-copy를 의미하지 않는다.
