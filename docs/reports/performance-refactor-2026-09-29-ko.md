# 통신·메모리·CUDA 성능 리팩토링 — 2026-09-29

실제 요청 경로를 따라 Python 제공자 → HTTP/SQLite 조정 서버 → SSE 추론 게이트웨이 → GPU 커널을 개선했다. 새 패키지 의존성과 DB 마이그레이션은 없다. 작업 시작 때 존재하던 수정 사항은 보존하고, 이번 변경 전 파일을 별도로 보관해 비교했다.

## 통신과 실행 흐름

Python의 공통 `request_json`이 스레드별 최대 두 origin 연결을 재사용한다. UTF-8 JSON에서 불필요한 공백과 한글 escape를 제거했다. URL·응답 크기·HTTP 오류 검증은 유지하며 POST를 임의로 다시 보내지 않는다. 다음 요청에서 유휴 시간이 4초를 넘은 연결은 닫고 새로 연결하며, 서버가 더 짧은 keep-alive를 알리면 그 기한에 여유를 두고 재사용을 중단한다. 별도 타이머로 소켓을 닫는 방식은 아니다. worker·설정 창·분산 실행기의 소유 스레드가 끝날 때도 연결을 닫는다. 모델 해시는 256KiB 버퍼를 재사용하면서 파일 전체를 읽는다.

새 제공자의 유휴 조회는 최대 10초 기다리는 선택적 long poll이다. 서버의 live 변경이 SQLite에 저장된 뒤 대기자를 깨우며, 응답 전에 인증·lease·작업 배정을 다시 검사한다. 제공자 완료 future도 즉시 깨워 기존 3초 주기의 불필요한 완료 지연을 없앴다. 실행 중 heartbeat 계약과 구버전 polling 호환은 유지한다. 합성 HTTP 검사에서 작업 등록 요청 시작→대기 제공자 응답은 최종 31.5ms였다(여러 실행 관측 범위 13.3–31.5ms). 저장 완료 시각을 별도로 계측한 값이나 GPU 추론 시간이 아니다.

조정 서버는 짧은 로컬 상태 변경을 하나의 실행 순서로 처리하고, CAS 검증은 유지한다. 20개 제공자가 동시에 조회할 때 새 작업 등록이 반복 충돌하는 문제를 재현하여 막았다. 10초 대기·추론·다운로드는 이 순서 안에서 기다리지 않는다. 알림은 단일 서버 프로세스 안에서만 동작하며 다른 프로세스가 DB를 바꾸면 최대 10초 뒤 조회에서 반영된다. 파일럿의 대기 한도는 전체 20개, 노드당 1개다.

정적 파일은 전체 파일을 메모리에 복사하지 않고 읽기 스트림으로 보낸다. ETag/304와 해시 자산의 장기 캐시를 적용했다. 전송 중 파일이 커지거나 작아지는 경우도 응답 프레이밍을 검사한다. Caddy는 `/assets/*`에만 zstd/gzip을 적용한다. Caddy 설정은 문법 문서를 확인했지만 이 장비에는 실행 가능한 Caddy/Docker daemon이 없어 프록시 실행 검증은 하지 못했다.

## 메모리 수명과 정산

SSE 검증기는 이미 전달한 답변 문자열을 다시 누적하지 않는다. 조각 경계·CRLF·UTF-8·usage·tool call·완료 검증을 유지하면서 파서를 선형으로 처리한다. JSON 응답만 필요한 최종 내용을 한 번 수집한다. `restart_on_failure:true` 공간의 출력은 바이트 기준 64KiB 큐와 소비자의 읽기 속도에 맞춰 전달한다. 읽는 중인 조각과 하위 스트림의 버퍼는 별도이므로 64KiB를 전체 메모리 상한이라고 표시하지 않는다.

기본 공간 SSE는 실패한 시도의 부분 답변을 노출하지 않기 위해 기존 4MiB 제한 아래 완성된 성공 시도를 모은다. 이를 무조건 조각 전달로 바꾸면 예비 전환 계약이 깨진다. 취소는 여러 호출자가 같은 erase ACK를 기다리며, ACK 전 슬롯을 재사용하지 않는다. 종료된 게이트웨이는 영수증을 다시 만들거나 백엔드를 재실행하지 않는다.

성공한 대여 task마다 과거 전체 문맥을 복제하던 부분을 제거했다. 현재 대화의 전체 60개 메시지는 job에 그대로 유지하고, 30개 과거 task에는 각 턴 사용자 메시지 30개만 둔다. 진행·실패·재시도 task의 문맥은 줄이지 않는다. 이미 저장된 오래된 데이터는 일괄 변환하지 않는다. 예약금·원장 검증을 한 번의 인덱스 생성으로 처리하고, 공개 snapshot에서 제외할 비공개 영수증을 먼저 복제하지 않는다.

Node 22.17.0의 기본 `Readable.toWeb`이 이미 바이트 기준 버퍼를 사용함을 런타임과 실험으로 확인했다. 이를 새 기능으로 다시 구현하거나 메모리 절감 실적으로 계산하지 않았다. 64MiB 원본의 정지된 소비자 시험에서 기존 동작은 128KiB를 미리 읽었다.

## GPU 직접 실행

CUDA Driver API로 소유 context·stream·메모리·이벤트·그래프를 생성하고 해제했다. 폭 4,096 F32 잔차·RMS 연산을 float4 접근, 레지스터 재사용, 독립 제곱합, warp shuffle로 개선하고 기본 블록을 1,024→128스레드로 줄였다. 공유 메모리는 블록당 128→16B, spill은 0이다. 32–1,024스레드를 비교했고 장비 보정 옵션을 남겼다.

잔차 합은 F32 기준 비트 동일하다. 정규화는 축약 순서가 바뀌므로 이전 결과와 비트 동일하지 않지만 기존 허용 오차 `2e-6 + 2e-6 × abs(reference)`를 만족한다. Q8_0 가중치와 f16 KV 계약, fast-math 비활성화는 유지했다. CUDA 그래프 안의 이벤트와 반복 순서를 섞은 15개 샘플 중앙값을 사용했으며 CPU 제출 간격을 커널 시간에 섞지 않았다.

**이 커널은 독립 검증 코드이며 llama.cpp 운영 그래프에 연결하지 않았다.** 전체 모델 소스·빌드·소비자 버퍼 계약과 logits 검증 없이 기존 DLL을 교체하지 않았다. 검사 프로그램의 GPU 데이터 할당 33.3% 감소도 비교용 출력 버퍼 재사용 결과이며 모델 VRAM 절감이 아니다. 실제 실행은 compute_86 장비만 검증했고 compute_75는 컴파일만 확인했다. GPUDirect/RDMA, NIC→GPU DMA, 두 PC 실측은 이번 결과에 포함하지 않는다. 상세 소스 해시·행별 수치는 `kernel-performance-2026-09-29-ko.md`와 `research/kernel-performance-20260929.json`에 있다.

## 검증과 재현

최종 Node 회귀 검사 **256/256**, Python **260개 통과·1개 Windows 플랫폼 제외**, 제공자 배포 패키지 검사 **9/9**, 브라우저 검사 **13/13**를 통과했다. lint·TypeScript 검사·프로덕션 빌드도 통과했다. 빌드는 기존 500kB 이상 JavaScript 번들 경고를 남기며 UI 코드 분할은 이번 변경에 포함하지 않았다.

20개 동시 제공자·관리자 등록, 실제 HTTP 16초 prefill, 연결 취소·키 회수·종료, 정적 파일 증감, 정산 불변식, 전체 대화 보존을 검사했다. Python 검사는 ResourceWarning을 오류로 취급했다. 실제 GPU는 기본 9개·경계 16개·epsilon 28개 사례와 출력 guard를 확인했으며, 호스트 launch 계약 자체 검사도 통과했다. 파서의 결정적 변형 입력 5,000개를 이전 구현과 비교하여 허용/거절 및 수집된 JSON 결과가 일치함을 확인했다.
