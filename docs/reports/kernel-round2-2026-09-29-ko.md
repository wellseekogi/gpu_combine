# CUDA 2차 검증 — 작은 행 분기와 하드웨어 한계

1차에서 개선한 128스레드 커널을 새로운 기준으로 삼아 다시 측정했다. 실제 RTX 3050 Ti에서 **1/8/16행은 512스레드가 각각 8.81%/6.90%/9.53% 빨랐다.** 검사 실행기는 16행 이하에만 이 경로를 선택한다. 17행 이상은 128스레드를 유지하며, 수동 `--threads` 설정은 항상 우선한다. 이 분기는 독립 커널 검사에 적용했으며 llama.cpp나 운영 제공자의 실행 그래프를 바꾸지 않았다.

## 유지한 수치 계약과 구현

폭 4,096의 연속 F32 입력, 최소 16바이트 정렬, 겹치지 않는 다섯 버퍼, 잔차 합과 정규화 출력 둘 다를 유지한다. 잔차 덧셈은 CPU F32 결과와 비트 동일해야 하며 모든 정규화 원소에 `abs(error) <= 2e-6 + 2e-6 * abs(CPU double)`를 적용한다. 축약 순서가 달라 정규화 결과의 비트 동일성을 주장하지 않는다. FMA·fast math·flush-to-zero를 켜지 않았고 모델 Q8_0·KV f16 계약을 바꾸지 않았다.

두 CUDA 진입점은 하나의 템플릿 구현을 사용한다. `residual_rms_f32`는 컴파일한 `RMS_THREADS`(기본 128), `residual_rms_f32_small`은 정확히 512스레드로 실행한다. 행당 블록 하나이며 호스트가 올바른 진입점과 스레드 수를 함께 선택한다. 기본 경로를 유지한 큰 행에서는 소스 정리로 인한 유의미한 속도 변화가 관찰되지 않았다. 두 출력은 이후 그래프 소비자가 필요하므로 제거하지 않았다. 2차 변경으로 데이터 버퍼 크기가 줄어든 것은 아니다.

최종 자동 분기 검사는 15개 사례(16/17 경계와 최대 1,024행 포함), 자동 그래프 재생 8개, epsilon `1.4e-45`와 `3e38` 각각 8개, 수동 32스레드 scalar 설정 7개를 모두 통과했다. 자동 경로 최대 절대 오차는 `9.87894e-7`, scalar 보정 검사는 `1.07700e-6`이었다. 두 PTX 대상이 컴파일되었고 실제 실행 대상은 compute_86이다. 128/512 경로의 드라이버 자원 보고는 각각 레지스터 **56/30개**, 공유 메모리 **16/64바이트**, 로컬 메모리 spill **0/0바이트**였다.

1차 기준 커널 SHA-256은 `04b0ba2bcf5c22aec333a47e9d60b6745fb399f046b7b29290c5f6a533a50591`, 최종 커널은 `b4b94c6dd90d0f0302f7eaf9be6db25c66d043a8326e4ad03b460a4239be9503`이다. 최종 검사기 해시는 `7e3a10a1190c42dde1bad336caebedd4adb520ba28fdcf9ff9777f3fcb2679d4`이며 모든 최종 검사 기록과 일치한다.

## 같은 실행 안의 비교

동일 버퍼와 CUDA stream에서 1차 원본 128, 템플릿 128, 템플릿 512 및 이전 참조들을 번갈아 실행했다. 그래프당 200회 연산, 최소 150ms 예열, 순서를 고정 seed로 섞은 15개 샘플이며 실제 GPU 이벤트 노드로 시간을 측정한다. 표의 감소율은 **1차 128스레드 기준**이다.

| 행 수 | 1차 128 µs | 512 µs | 시간 감소 | 감소율 bootstrap 95% 구간 |
|---:|---:|---:|---:|---:|
| 1 | 3.200 | 2.918 | 8.81% | 2.46–11.87% |
| 8 | 4.009 | 3.732 | 6.90% | 4.83–11.03% |
| 16 | 5.801 | 5.248 | 9.53% | 2.60–16.48% |
| 17 | 5.453 | 4.874 | 10.61% | −0.82–20.36% |
| 31 | 12.575 | 11.443 | 9.00% | 0.77–14.66% |
| 32 | 27.945 | 25.088 | 10.22% | 8.57–10.91% |
| 33 | 51.686 | 49.562 | 4.11% | 3.40–4.71% |
| 128 | 404.987 | 413.517 | −2.11% | −2.16–−2.08% |

구간은 각 구현의 15개 샘플을 독립 재추출하여 중앙값 비율을 5,000번 계산한 결과다(seed 77). 클록·전력의 장기 변동까지 보장하는 구간은 아니다. 앞선 독립 실행에서도 1/8/16행의 감소 방향을 확인했다. 17행 이상으로 분기를 확장하지 않은 이유는 경계 부근의 변동과 큰 행의 명확한 역효과 때문이다.

## 전력 상태 때문에 절대 시간을 섞지 않는다

2차 측정 중 드라이버는 **현재·요청 전력 한도 20W, 기본 한도 60W**, 부하 중 메모리 클록 **810MHz**와 소프트웨어 전력·열 제한을 보고했다. 1차는 6,001MHz 조건이었다. 코드나 도구로 전력·클록·드라이버·운영체제 설정을 변경하지 않았다. 따라서 1차의 2.125µs와 2차의 2.918µs를 이어서 성능 향상이나 퇴보로 계산하면 안 된다. 각 행의 비교는 같은 실행의 기준과 후보 사이에서만 한다.

257행은 입력 두 개 읽기와 출력 두 개 쓰기만 합쳐 16,842,752바이트다. 2차 독립 비교의 821.832µs 기준으로 약 **20.49GB/s의 유효 데이터 처리율**이다. 가중치 읽기, 실제 캐시/DRAM 거래, 그래프 스케줄링은 이 단순 계산에 포함하지 않는다. 하드웨어 카운터로 측정한 DRAM 대역폭이나 이론적 한계 도달률이라고 주장하지 않는다. 큰 행에서 다양한 연산 배치가 비슷한 시간으로 수렴한 관찰은 메모리 전송이 제한한다는 해석과 일치한다.

## 시도했지만 기본값에 넣지 않은 변경

- warp 하나/둘/넷으로 행을 계산하고 2/4/8행을 블록에 묶는 변형은 경계 guard와 수치 검사를 통과했다. 초기 광범위 비교 중 별도의 `llama-bench --help`가 CUDA context를 생성한 사실을 확인했으므로 그 실행의 시간은 채택 근거에서 제외한다. 다른 CUDA 프로그램 없이 다시 측정한 warp 32스레드×4행 변형은 257행에서 821.668→798.853µs로 **2.78%** 빨랐지만, 1행은 3.359→8.284µs로 느려졌다. 레지스터는 166개/스레드다. 큰 행의 더 넓은 범위와 다른 전력 상태에서 분기 기준을 검증하지 못했으므로 기본값 채택을 보류했다. 더 개선할 수 없다는 증명은 아니다.
- 합을 레지스터에 보관하지 않고 출력 버퍼에서 다시 읽는 변형은 레지스터를 56→43개로 줄였다. 하지만 독립 재검증에서 1행 3.359→3.891µs, 257행 821.668→991.785µs로 느려져 채택하지 않았다.
- 입력에 PTX `ld.global.cg`를 쓰면 작은 1/8/16행이 느려졌다. `st.global.cs`는 33행 반복 버퍼에서 48.891→27.592µs로 빨랐지만 128/257행에서는 유의미한 이득이 없었다. 출력에 조기 퇴출 힌트를 주므로 실제 다음 그래프 소비자의 재사용을 포함한 이득을 증명하지 못한다. 합성 반복의 캐시 경계 이득만으로 기본 정책을 바꾸지 않았다.
- 첫 광범위 비교의 시간과, 이후 CUDA 프로그램이 겹치지 않게 실행한 비교를 증거 파일에서 구분했다. 더 느린 변형이나 미확인 캐시 정책을 최종 커널에 남기지 않았다.

캐시 지정자는 메모리 일관성을 바꾸지 않는 성능 힌트이고 `.cs`는 조기 퇴출을 지시한다. 판단 근거는 [NVIDIA PTX ISA 8.4 캐시 연산자](https://docs.nvidia.com/cuda/archive/12.4.1/parallel-thread-execution/index.html#cache-operators)다.

## 설치 자원 확인과 운영 통합의 경계

읽기 전용 검색으로 고정 실행기 `.relay/runtimes/llama-b10964-cuda12.4`를 확인했고, 실행기가 보고한 버전은 **b10964, commit b29c606e2, Clang 20.1.8**이다. `llama-bench.exe`, CUDA DLL과 Qwen3-4B Instruct/Thinking Q3_K_M 모델(각 약 2.076GB)이 실제로 존재한다. 요청된 Qwen3-8B Q8_0 전체 모델은 검색 범위에서 찾지 못했다. 별도의 Transformers 모델은 발견했지만 이 실행기의 비교 대상으로 사용하지 않았다.

NVRTC 12.4 DLL, CMake/Ninja 및 Visual Studio C++ 컴파일러 파일은 존재한다. nvcc는 PATH와 확인한 CUDA 설치 경로에서 찾지 못했으며, 작업 폴더의 upstream b10964 자료는 여덟 소스 발췌본이다. 완전한 CUDA 빌드 트리와 요청 모델을 검증하지 못한 상태에서 기존 DLL을 교체하지 않았다. 작은 모델이 있다는 이유로 Q8 계약을 Q3으로 바꾸지 않았다. 1660 SUPER 실제 실행, 두 PC 통신, 커널이 연결된 모델 logits와 전체 지연은 여전히 별도 검증이 필요하다.

## 별도의 실제 모델에서 측정한 메모리·속도 절충

설치된 Qwen3-4B-Instruct-2507.Q3_K_M 파일을 그대로 읽어 고정 `llama-bench`로 측정했다. 모델 SHA-256은 `42fd3a1a10a371d1a926ac7dee7e33d4b4389ddde7a0282f788849a0b979f8f8`다. 오프라인 실행, CUDA0, `-ngl 99`, f16 K/V, CPU 스레드 8개, 논리 배치 512, 각 조건 3회 반복을 명시했다. 이 모델의 hidden width는 **2,560**이므로 폭 4,096의 실험 커널이 연결된 결과가 아니다. 바이너리·모델·제공자 설정은 변경하지 않았다.

실행기 로그는 **37/37층 GPU offload**, GPU 모델 버퍼 **1,973.78MiB**, CPU-mapped 모델 버퍼 **304.28MiB**를 보고했다. 따라서 모든 데이터가 GPU에만 있다는 주장은 하지 않는다. 아래는 flash attention on에서 물리 배치(ubatch)를 바꾼 결과이며 실행기가 보고한 평균±표준편차다.

| 입력 토큰 수 | ub128 토큰/s | ub256 토큰/s | ub512 토큰/s | f16 GPU KV MiB |
|---:|---:|---:|---:|---:|
| 512 | 464.91±0.74 | 527.21±0.61 | 577.53±10.81 | 72 |
| 2,048 | 453.15±0.17 | 516.76±0.41 | 567.31±0.15 | 288 |
| 4,096 | 437.84±0.43 | 498.47±0.35 | 542.97±0.95 | 576 |

GPU 작업 버퍼는 ub128/256/512에서 각각 **75.44/150.88/301.75MiB**였다. 4,096토큰에서 ub512는 ub128보다 약 24.01% 높은 처리량을 보였지만 작업 버퍼는 네 배다. 이 결과는 배치를 무조건 최소화하면 처리 속도를 잃는 실제 절충을 보여준다. 관찰된 전체 GPU 사용량 최대는 약 **2,947MiB**였으며 1초 간격 표본의 최대값이라 순간 최고값을 보장하지 않는다. 부하 표본의 메모리 클록은 모두 810MHz였다.

처음 실행한 256토큰 보조 비교는 flash on/ub256 약 511.77토큰/s, flash off/ub512 약 422.87토큰/s였다. 이 경우 요청 ub512는 실제 ub256으로 잘렸기 때문에 512 물리 배치 성능이라고 부르지 않는다. 위 512~4,096토큰 추가 측정에서는 요청한 물리 배치가 실제 적용되는 것을 로그로 확인했다.

생성 단계는 따로 `-p 0 -n 32 -d N`으로 검사했다. 기존 prefix를 준비·복원하는 시간은 측정 구간 밖이고, 그 뒤의 32토큰 연산만 측정한다. 일반 `-p N -n 32`에서 나오는 빈 문맥 생성 수치를 긴 문맥 결과로 잘못 해석하지 않도록 [고정 b10964 benchmark 소스](https://github.com/ggml-org/llama.cpp/blob/b10964/tools/llama-bench/llama-bench.cpp)를 확인했다.

| 기존 prefix 토큰 | 생성 토큰/s | 실제 할당 문맥 | f16 GPU KV MiB |
|---:|---:|---:|---:|
| 512 | 9.24±0.03 | 768 | 108 |
| 2,048 | 8.41±0.04 | 2,304 | 324 |
| 4,096 | 7.51±0.03 | 4,352 | 612 |

문맥 할당은 prefix+32에 맞춰 내부 정렬로 커진다. 이 실험은 4,096토큰까지 실제 실행한 결과이며 8,192토큰의 적재 성공이나 OOM을 주장하지 않는다. 8,192토큰은 KV만 약 1,152MiB가 필요하고 ub512의 모델·KV·작업 버퍼 합계만 약 3,427.53MiB다. 여기에 드라이버/context 등 추가 메모리가 필요하므로, 실행기가 초기 확인에서 보고한 가용 3,287MiB를 기준으로 무리하게 적재하지 않았다. 이론상 용량 계산과 실제 검증 범위를 구분한다.

다른 모델·양자화·KV 타입·문맥·GPU로 이 수치를 일반화하지 않는다. flash 설정 사이의 전체 logits 일치성 검사는 하지 않았으며 해당 설정을 운영 Q8 기본값에 적용하지 않았다. 생성 benchmark는 지연 측정용 합성 토큰 작업이고 답변 품질 평가가 아니다.

## 호스트 prompt cache를 끈 실제 동작 검사

추가로 두 개의 자체 소유 loopback 서버를 순차 실행해 합성 prompt `A,A,B,B,A,A`를 비교하고 종료했다. 같은 모델·f16·greedy seed로 `--cache-ram 8192 --cache-idle-slots`와 `--cache-ram 0 --no-cache-idle-slots`를 비교했으며 **여섯 응답의 내용 해시가 모두 같았다.**

두 모드 모두 연속된 A 반복에서 기존 GPU prefix 304토큰을 재사용하고 1토큰만 평가했다. RAM cache를 켠 경우 B→A 전환도 304토큰을 복원했지만, 끈 경우에는 A의 305토큰을 다시 계산했다. 활성 GPU 슬롯의 prefix 재사용과 과거 prompt의 RAM 보관은 별도 기능이라는 것을 실제 응답 계측으로 확인했다.

RAM cache 활성 로그에는 **43.317MiB / 51.755MiB** 상태 저장과 각각 **60.36ms / 97.43ms** cache 갱신이 기록되었다. 비활성 로그에는 이 상태 저장이 없다. 8,192MiB 기본값은 상한이며 그만큼 미리 할당하거나 항상 절감하는 것은 아니다. 프로세스 private bytes도 원시 자료에 기록했지만 드라이버·매핑·할당기 변동이 섞이므로 이를 곧바로 순수 cache 절감량이라고 부르지 않는다. 서로 다른 과거 prompt를 오가며 재사용하는 작업에서는 비활성화가 느려질 수 있다.

[고정 서버 소스](https://github.com/ggml-org/llama.cpp/blob/b10964/tools/server/server-context.cpp)의 RAM cache 생성 조건과 live-slot prefix 재사용 조건도 함께 확인했다. 이 기능을 운영 실행기에 적용할 때는 제공자 측에서 실제 실행기의 도움말 지원 여부를 확인해야 한다. 도움말 실행 자체도 CUDA 초기화를 할 수 있으므로 실행 중인 추론과 겹쳐 수행하지 않는다.

제공자의 실제 `runtime_cache_options()` 함수를 설치된 실행기에 한 번 호출한 검증에서도 `--cache-ram 0 --no-cache-idle-slots`가 반환되었다. 소요 시간은 약 2.35초였으며 lease나 모델 요청과 겹치지 않게 실행했다. 최종 점검 시 소유 서버·benchmark 프로세스는 남아 있지 않았고 GPU 사용량은 다시 0MiB/0%였다.
