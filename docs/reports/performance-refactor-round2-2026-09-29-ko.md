# 통신·메모리·커널 2차 최적화 — 2026-09-29

1차 개선을 새 기준으로 삼아 남은 비용을 다시 측정하고 소스를 추가로 변경했다. 새 의존성과 DB 마이그레이션은 없다. 기존 작업 내용은 보존했으며 이번 비교는 Git HEAD가 아니라 2차 시작 시 보관한 파일을 기준으로 한다.

모든 환경에서 더 빠른 구현이 불가능하다는 수학적 증명을 한 것은 아니다. 실제로 시험한 후보, 채택한 변경, 손해가 나서 제외한 변경과 이 장비에서 검증할 수 없는 경계를 구분했다.

## 추가로 적용한 변경

- 상태 조회는 저장소에서 방금 읽은 독립 객체를 응답 생성에 사용해 중복 깊은 복사를 없앴다. 직접 engine 함수를 호출하는 기존 사용자는 계속 독립 snapshot을 받는다. 회원 조회의 GPU 점유 여부와 예약금 계산도 반복 검색 대신 한 번 계산한다. 인증용 해시는 같은 UTF-8 SHA-256 결과를 내는 Node 기본 구현으로 바꿨다.
- 유지보수는 최대 64개 풀의 `revision`과 다음 만료 시각만 기억한다. 상태 자체나 인증 정보는 보관하지 않는다. 버전이 같고 아직 만료할 작업이 없으면 큰 JSON을 다시 해석하지 않는다. 동시에 기존 타이머가 놓치던 유휴 GPU 대여의 45초 연결 만료도 처리하며, heartbeat가 갱신되면 새 만료 시각을 적용한다.
- 인증된 관리자·회원의 상태 GET 응답에만 Brotli quality 1/window 16과 gzip level 1/window 13/memory level 6을 협상한다. 응답은 계속 `no-store`이며 `Vary: Accept-Encoding`, 압축 해제 후 동일 내용, q=0 거부와 identity 우선순위를 검사한다. 키를 반환하는 POST, 오류, SSE, 모델 파일은 이 압축 대상에 포함하지 않는다.
- HTTP 송신은 Node가 Web 스트림을 직접 소비하게 해 중간 변환의 추가 선읽기를 없앴다. 모델 다운로드는 필요할 때 최대 256KiB만 읽으며, 파일 크기·실행 권한·취소·조기 EOF를 계속 검사한다. 업로드는 기본 write-stream의 쓰기 묶음 처리와 fsync를 사용한다.
- Python 모델 다운로드의 읽기 단위를 256KiB로 줄이고 쓰기·해시 처리 직후 버퍼 참조를 해제한다. 선택된 실행기가 기능을 지원하면 CPU RAM의 과거 프롬프트 snapshot만 비활성화한다. 기능 확인은 인증 후 첫 lease 전에 한 번 하며, 오래된 실행기는 기존 옵션으로 실행한다. 현재 GPU 슬롯의 f16 KV 재사용은 유지한다.
- SSE는 흔한 LF 행을 기본 문자열 검색으로 처리하고, 여러 data 행이 있을 때만 배열을 만든다. 재시작 지원 출력 큐는 조각 1개로 줄이되 상류 선읽기는 유지한다. 빈 조각도 큐에서 세며 완료 검증·취소 ACK를 유지한다. 독립 CUDA 커널은 하나의 템플릿 구현으로 16행 이하의 512스레드 경로와 나머지 128스레드 경로를 선택한다.

## 측정 조건과 결과

동일 실행의 기준·후보를 번갈아 측정했다. 서버·통신 수치는 합성 상태 또는 loopback이며 WAN이나 두 PC 성능을 뜻하지 않는다. 실제 모델 시험은 보유한 보조 Qwen3-4B Q3_K_M과 f16 KV를 사용했으며 운영 Q8 모델 계약은 바꾸지 않았다.

조회 결과를 GC 뒤 계속 보유하는 시험에서는 관리자 heap이 약 1.70→1.65MB, 회원은 0.963→1.098MB였다. 따라서 이 변경을 모든 응답의 보유 메모리 감소로 표시하지 않는다. 주된 이득은 깊은 복사 비용 제거다. 모델 전송 큐·Python 할당·SSE 버퍼 수치 역시 각각 측정 범위가 다르며 합산해 전체 RAM 절감률로 표시하지 않는다.

Brotli와 gzip의 비교에는 속도·전송 크기·동시 압축기의 메모리 관측을 함께 사용했다. 16개 압축기의 RSS 차이는 allocator와 스레드 상태에 영향을 받으므로 고정 상한으로 사용하지 않는다. gzip의 deflate 작업 메모리는 공식 계산상 기본 256KiB에서 64KiB로 줄어들지만 객체와 출력 버퍼는 별도다. [Node 22.17 zlib 메모리 설명](https://nodejs.org/download/release/v22.17.0/docs/api/zlib.html#memory-usage-tuning), [HTTP 인코딩 협상 규칙](https://www.rfc-editor.org/rfc/rfc9110.html#name-accept-encoding).

## 남은 비용과 제외한 후보

최종 관리자 조회의 별도 구성 요소 측정은 JSON 해석 약 13.09ms, 응답 JSON 생성 약 20.17ms였다. 전체 약 35.58ms와 비교하면 남은 비용의 대부분은 현재 저장·응답 형식에서 온다. 더 줄이려면 저장 구조 분해, 응답 필드 축소, 변경분 프로토콜 등의 별도 계약 변경을 측정해야 한다. 현재 자료만으로 그 효과나 불가능성을 단정하지 않는다.

모델 읽기를 128KiB로 더 줄이면 HTTP 버퍼는 작아지지만 시험의 전송 시간이 약 16% 늘었다. 최종 256KiB와 기본 Web pipeline의 조합은 느린 수신자 시험에서 기준과 같은 약 393KB의 ArrayBuffer 증가량을 보였다. 이 값은 로컬 송신자·수신자와 헤더를 포함하는 GC 관측이며 OS/TLS 버퍼나 전체 RSS의 상한이 아니다.

CPU 프롬프트 snapshot을 끄면 실제 보조 모델 시험에서 43.3/51.8MiB의 저장과 60.4/97.4ms의 갱신 비용이 사라졌다. 같은 문맥을 연속 사용하면 304토큰 재사용이 유지됐지만, 다른 문맥을 거쳐 과거 문맥으로 돌아갈 때에는 305토큰을 다시 계산했다. 기본 RAM cache의 8GiB 설정은 상한일 뿐이며 8GiB가 실제로 절약됐다고 주장하지 않는다.

실행기 기능 확인은 이 장비에서 최초 한 번 약 2.35초가 걸렸다. 인증·계약 출력·GUI 파일 검사에서는 실행하지 않고 실제 제공 시작 때만 수행한다. 시간 초과·지원하지 않는 도움말은 기존 옵션으로 돌아간다.

SSE의 상류 선읽기까지 없애면 버퍼 한 조각을 더 줄일 수 있었지만, 이를 분리한 HTTP 시험에서 재시작 스트리밍이 약 8.7% 느려져 제외했다. 여러 data 행을 무조건 문자열로 이어 붙이는 후보도 65,536개 빈 행에서 약 2.10MiB를 유지해, 약 0.65MiB의 지연 배열 방식으로 대체했다. JSON의 스트리밍 TextDecoder는 17~32% 느렸고 효과가 불안정한 필드 펼치기·await 우회도 적용하지 않았다.

4,096토큰 실제 prefill에서 microbatch 128/256/512는 437.84/498.47/542.97 tokens/s였고 compute workspace는 75.44/150.88/301.75MiB였다. 속도와 VRAM 사이의 교환 조건이므로 보조 모델 결과만으로 모든 제공자의 기본 배치를 키우지 않았다. 같은 모델의 실제 긴 prefix 후 decode는 512/2,048/4,096토큰에서 9.24/8.41/7.51 tokens/s였다.

CUDA 큰 행의 여러 배치는 비슷한 데이터 처리율로 수렴했다. 일부 행 묶음·캐시 힌트는 특정 모양만 개선하거나 작은 입력을 크게 악화시켜 기본값에 넣지 않았다. 16행 이하의 선택 분기만 채택했으며 수동 보정 옵션을 유지한다. 자세한 후보·오차·측정 방법은 `kernel-round2-2026-09-29-ko.md`에 있다.

## 검증 범위와 한계

최종 전체 Node 검사 **264/264**, Python **264개 통과·1개 Windows 플랫폼 제외**, 브라우저 **13/13**, 제공자 패키지 **9/9**로 총 **550개 통과**다. lint·TypeScript 검사·프로덕션 빌드도 통과했다. 빌드는 기존 500kB 이상 JavaScript 번들 경고를 남긴다. 새 벤치마크의 정리 코드 린트 오류 2개는 경로 검사를 앞 단계로 옮겨 수정하고 재검사했다.

SSE 입력 10,000개의 허용·거절 및 수집 결과를 2차 기준과 비교해 일치를 확인했다. 모델 전송의 짧은 쓰기·fsync 실패·중단·기한 회수·읽기 중 취소·닫기 실패, 새 유지보수 캐시의 정확한 만료 시각과 heartbeat 갱신, 실제 HTTP 압축과 파일 증감도 검사했다. Python ResourceWarning은 오류로 취급했다.

GPU 최종 검사는 자동 형상 15개, 자동 그래프 재실행 8개, 극단 epsilon 16개, 수동 scalar 형상 7개로 **46개 실행**과 호스트 계약 자체 검사를 통과했다. compute_75/86은 컴파일했고 실제 실행은 compute_86이다. 실제 보조 모델은 22개 조건을 기록했으며 캐시 정책 비교의 6개 출력 해시가 같았다. 소유한 모델·검사 프로세스는 종료했다.

GPU는 RTX 3050 Ti Laptop 4GiB, 2차 부하 중 전력 한도 20W·메모리 클록 810MHz였다. 1차의 다른 전력 상태와 절대 시간을 섞지 않았다. 소유한 CUDA context와 테스트용 모델 프로세스만 사용했고 전력·드라이버·OS 설정은 변경하지 않았다. 8,192토큰 배치는 여유 VRAM 계산이 부족하여 시험하지 않았으며 OOM을 관측했다는 뜻이 아니다.

독립 CUDA 커널은 운영 llama.cpp 그래프에 아직 연결되지 않았다. 완전한 CUDA 빌드 소스·nvcc와 대상 Q8 모델을 검증하지 못했고, 두 PC/RDMA/GPUDirect 및 1660 SUPER 실측도 없다. 이번 자료가 증명하는 것은 명시된 입력·하드웨어에서의 개선과 실패한 후보의 결과다.
