# 분산 실행 코어·연산 커널 개발 기록

## 인터뷰 결정

- Windows + NVIDIA: 노트북 RTX 3050 Ti 4GiB, 데스크탑 GTX 1660 SUPER 6GiB.
- 한 GPU에 들어가지 않는 모델의 안정적인 분산 실행을 우선한다.
- 배포된 AWS 사이트가 제어하고 두 PC는 LAN으로 직접 계산 데이터를 주고받는다.
- PC 이탈 시 진행 요청은 실패 처리한다. 재연결 후 전체 기록으로 재실행한다.
- 가중치 양자화·KV 정밀도를 유지한다. 손실 압축·CPU 자동 대체·실행 중 레이어 이동은 없다.
- 데스크탑 검증 지휘와 결과 전달에는 기존 Agent Relay 연락방을 사용한다. 장비·모델·연결 정보 요청은 자동 승인 검토에서 거절되어 전송되지 않았다. 해당 범위의 명시적 승인 전에는 보내지 않는다.

민감한 내용을 뺀 연결 확인은 승인되었다. 기존 `relay-lead`는 설치된 SDK의 신규 등록 동작 때문에 이름 충돌이 발생했다. 기존 신원을 변경하지 않고 이번 채팅을 같은 방의 `relay-kernel-lead`로 등록했다. `relay-desktop`에 정보 없는 연결 확인 요청을 대기열에 넣었으나 오프라인으로 표시되어 수신·ACK는 확인되지 않았다. 확인용 MCP 프로세스는 이후 종료되었고 메모리 토큰은 보관하지 않았다. 다음 연결에는 해당 신원의 지원되는 복구가 필요하며 같은 이름의 신규 등록을 반복하면 안 된다. 장비 조사·개발 파일 공유는 아직 전송하지 않았다. 새 Codex 프로세스나 연락방은 생성하지 않았다.

## 검증 모델

[공식 Qwen3-8B Q8_0 GGUF](https://huggingface.co/Qwen/Qwen3-8B-GGUF)를 선택했다. 파일 크기는 8,709,518,112바이트다. 전체 모델 대신 제한된 GGUF 헤더를 읽어 텐서 크기·연속 offset·전체 파일 크기를 교차 확인했다. 전체 SHA-256은 게시자의 LFS 메타데이터 값이며 실행 전에 실제 내려받은 전체 파일을 다시 해시해야 한다.

- revision: `7c41481f57cb95916b40956ab2f0b139b296d974`
- 모델 SHA-256: `408b955510e196121c1c375201744783b5c9a43c7956d73fc78df54c66e883d6`
- 템플릿 SHA-256: `57f1fd00f0013a2be96aa79b857391f27e23df5b5f847072b524c897e24d0361`
- 36개 레이어 각각 205,030,400바이트. 마지막 GPU의 출력층·정규화 가중치는 661,241,856바이트.
- CPU 입력 임베딩은 661,225,472바이트. llama.cpp의 정상 배치이며 장애 시 CPU 대체가 아니다.
- GPU 가중치 합계는 8,042,336,256바이트(약 7.49GiB). CPU 임베딩을 제외해도 6GiB 한 장에 모두 들어가지 않는다.

배치 근거는 b10964의 [장치 배치](https://github.com/ggml-org/llama.cpp/blob/b10964/src/llama-model.cpp), [텐서 분류](https://github.com/ggml-org/llama.cpp/blob/b10964/src/llama-arch.cpp), [로더](https://github.com/ggml-org/llama.cpp/blob/b10964/src/llama-model-loader.cpp)다. 양자화는 처음부터 Q8_0으로 고정하며 전용 커널과 비교할 때도 같은 파일을 사용한다.

첫 조건: 동시 요청 1개, 문맥 2,048, f16 K/V. GPU별 workspace 384MiB·reserve 512MiB는 **측정 전 예산**이다.

| GPU 순서 | 담당 레이어 | 가중치 예산 | KV | workspace + reserve | 잔여 용량 |
|---|---:|---:|---:|---:|---:|
| 노트북 3050 Ti | 0–14, 15개 | 2,933MiB | 120MiB | 896MiB | 147MiB |
| 데스크탑 1660 SUPER | 15–35, 21개 + 출력층 | 4,737MiB | 168MiB | 896MiB | 343MiB |

잔여 용량은 reserve까지 뺀 계산값이며 실제 여유 VRAM이나 적재 성공을 보증하지 않는다. 노트북 총 4,096MiB는 장비에서 확인했고 데스크탑과 두 PC 동시 실행은 아직 미검증이다. 초기 workspace를 줄이기 위해 서버 실행 시 `--batch-size 512 --ubatch-size 128`을 명시한다. 두 옵션을 생략하면 기존 동작을 유지하며, 둘을 함께 지정할 때 `1 ≤ ubatch ≤ batch ≤ 슬롯 문맥`을 검사한다. RPC worker 옵션은 아니다.

## 구현된 코어

`planTwoGpuLayers`는 모델 해시가 일치하는 텐서 크기와 두 GPU 예산으로 모든 연속 레이어 경계를 검사한다. 가중치·슬롯별 f16 KV·workspace·reserve를 포함해 작은 쪽 잔여 용량을 최대화한다. **용량 기반 계획이며 실측 속도 최적화가 아니다.** 입력은 복제하고 이전 배치의 성능 선언은 제거한다. 결과는 기존 전체 설정 검증을 다시 통과해야 한다.

```powershell
node scripts/plan-two-gpu.mjs docs/examples/qwen3-8b-two-gpu.config.json docs/examples/qwen3-8b-q8_0.weights.json qwen8-two-gpu inference.local.json
```

이미 있는 출력 파일은 덮어쓰지 않는다. GPU 식별자·인증 키·실측 메모리 예산을 반영하고 실행 중인 기존 그룹을 정상 종료한 뒤 적용한다. 실행 중 KV를 이동시키지 않는다.

`snapshot().groups[].lastAttempt`에는 마지막으로 정리까지 끝난 시도 하나만 기록한다. `outcome`은 `success/failure`이며 다음 필드를 단조 시계로 측정한다.

| 필드 | 의미 |
|---|---|
| `prepareMs` | 엔진 계약 확인·공유 초기 준비(KV 초기 삭제 포함) |
| `inputValidationMs` | 정확한 입력 토큰 계산·문맥 검사 |
| `kvEraseMs` | 요청별 기존 KV 교체 |
| `backendFirstOutputMs` | backend 호출부터 첫 실제 SSE 내용·추론·도구 호출까지 |
| `backendTotalMs` | backend 호출부터 응답 소비 종료까지, 실패 정리 제외 |
| `cleanupMs` | 실패 뒤 KV 삭제 ACK 대기 |
| `totalMs` | 정리까지 포함한 시도 전체 경과 시간 |

미실행 단계와 비스트리밍 JSON의 첫 출력 시간은 `null`이다. 프롬프트·키·세션 식별자를 기록하지 않는다. 소비자 읽기 대기와 전송이 포함될 수 있어 GPU 계산 시간이나 decode 속도로 해석하면 안 된다. 기존 `generationMs` 의미는 유지했다.

## 두 PC와 배포 사이트

권장 역할은 **노트북=첫 단계 RPC, 데스크탑=마지막 단계와 leader**다. 모델 전체는 데스크탑에 두고 `--device RPC0,CUDA0` 순서를 실제 장치 목록과 대조한다. 마지막 단계와 샘플링을 같은 PC에 두어 큰 출력 logits의 원격 복사를 피할 가능성이 있지만, 실제 통신량 개선은 아직 미측정이다.

```text
배포 사이트 ── 인증된 터널 ── 데스크탑 leader / 1660 SUPER
                               └── 내부망 RPC ── 노트북 / 3050 Ti
```

기존 gateway는 upstream loopback만 허용한다. AWS→데스크탑의 인증된 터널이 별도로 필요하며 `--coordinator` 상태 알림만으로 모델 호출 경로가 열리지 않는다. Docker 배포라면 **gateway 컨테이너 내부의** `127.0.0.1:8082`가 터널에 연결되어야 한다. raw RPC는 인터넷에 공개하지 않는다. 내부망 직접 연결은 PC 간 통신이며 NIC→GPU GPUDirect를 뜻하지 않는다.

명령·해시·키·방화벽은 [분산 운영 문서](distributed-inference-ko.md)를 따른다. 예제 설정은 인증 키가 없는 준비용 파일이며 운영 서버에 자동 적용하지 않는다. Agent Relay는 연락 채널이고 모델·코드·GPU 데이터 통신을 자동 공유하지 않는다.

## 첫 전용 연산 커널 후보 (2026-09-27 초기 기록)

b10964에는 RMSNorm→곱셈 융합이 이미 있다. 새 후보는 Qwen3 FFN 직전의 **잔차 덧셈→RMSNorm→가중치 곱셈**이다. 이후 잔차 경로에서 덧셈 결과를 다시 사용하므로 합산 결과와 정규화 결과를 모두 출력해야 한다. FP32와 원래 덧셈 반올림을 유지한다.

후보 범위는 연속 메모리·폭 4,096의 F32 텐서다. decode에는 선행 MatVec+ADD 융합이 있어 주된 검증 대상은 prefill이다. `kernels/residual-rms-f32.cu`와 `scripts/check-cuda-kernel.py`에 독립 커널·검사를 구현했다. GPU 데이터 버퍼는 최대 24.11MiB이며 시스템 설치 없이 작업 폴더의 NVIDIA NVRTC를 사용한다. 실행 방법·컴파일러 출처는 [커널 안내](../kernels/README.md)에 있다.

RTX 3050 Ti에서 무작위·영벡터·상쇄·작은 값, 행 수 1/3/5/7/33/257의 6개 검사를 통과했다. 덧셈 결과는 CPU의 FP32 반올림 결과와 비트 단위로 같고, 정규화 결과는 동일 합산 순서의 두 번 실행 참조 커널과 같았다. CPU 배정밀도 기준 최대 절대 오차는 `7.44e-7`, 허용식은 `2e-6 + 2e-6 × abs(reference)`다. 기존 llama.cpp 바이너리와 비트 동일하다는 주장은 아니다.

compute_75·compute_86 PTX를 모두 컴파일했으며 실제 실행은 compute_86만 검증했다. CUDA 이벤트 시간에는 Python 실행 요청 간격이 포함되고 그래프 재생을 사용하지 않아 속도 향상 근거로 쓰지 않는다. 독립 검사 통과는 llama.cpp 그래프 통합이나 전체 모델 속도 향상을 증명하지 않는다. 현재 기본 실행은 검증된 llama.cpp 경로다.

## 2026-09-29 커널 최적화 후속

GPU 실측으로 vector F32 접근·128스레드 블록·warp 축약을 적용했고 CUDA 그래프 안의 이벤트로 Python 요청 공백을 제거했다. 같은 실행에서 이전 융합 커널 대비 1/33/128/257행 시간이 각각 6.10%/16.01%/5.59%/2.60% 줄었다. 257행 비교 검사 할당은 24.11→16.08MiB이며 **검사 프로그램의 출력 버퍼 재사용 효과**다. 모델 VRAM 감소는 아니다.

잔차 합의 비트 동일성과 기존 CPU double 허용 오차를 유지한다. 정규화 축약 순서는 달라 이전 정규화와 비트 동일하지 않다. GPU 출력 guard·형상 경계·극단 epsilon·그래프 재생 출력도 검사했다. 운영 llama.cpp 통합과 compute_75 실제 실행은 아직 미검증이다. 자세한 수치·제약·재현 명령은 [후속 보고서](reports/kernel-performance-2026-09-29-ko.md), 원시 샘플은 [검증 JSON](research/kernel-performance-20260929.json)에 있다.

## 2026-09-29 2차 커널·실제 실행기 조사

1차 커널을 기준으로 행 묶음·레지스터 재읽기·캐시 정책·작은 행 스레드 수를 다시 비교했다. 검사 실행기는 16행 이하에 512스레드를 선택하며 같은 실행의 128스레드보다 1/8/16행 시간이 8.81%/6.90%/9.53% 줄었다. 큰 행은 128스레드를 유지한다. 운영 llama.cpp 그래프는 바꾸지 않았다.

2차에서 관찰한 현재 전력 한도는 20W, 부하 중 메모리 클록은 810MHz였다. 1차와 다른 전력 상태이므로 절대 시간을 섞지 않는다. 실제 설치된 b10964 실행기와 별도의 Qwen3-4B Q3_K_M 모델을 찾아 보조 전체 모델 측정도 진행했다. 이 모델은 Q8_0 운영 계약을 대체하지 않는다. 수치·작업 버퍼·미채택 대안·자원 검색 범위는 [2차 보고서](reports/kernel-round2-2026-09-29-ko.md)에 기록한다.

## 검증 상태 (2026-09-27)

- 용량 계획과 기존 계획 회귀 18개 통과.
- 계측·workspace·HTTP·audit 회귀 70개 통과.
- 분산 실행기 회귀 16개 통과.
- 실행기 GUI 회귀 13개 통과. 위 자동 검사 합계 117개다.
- 실제 노트북 GPU 커널 검사 6개 통과. GPU 버퍼·소유 context 정리 후 사용량이 이전 수준으로 돌아온 것을 확인했다.
- 두 PC 모델 적재·최고 VRAM·처리 시간·연결 끊김 검증은 데스크탑 연결 후 진행한다.
- 원격 배포는 아직 하지 않았다. 기존 미커밋 작업이 많으므로 전체 작업 폴더를 임의로 배포하지 않는다.

다음 인터뷰는 실제 메모리에 따른 문맥/작업 버퍼 조정과 수치 오차·전체 실행 계측을 통과한 후보의 적용 범위를 다룬다.
