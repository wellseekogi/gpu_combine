# Relay: 아키텍처 검토와 구현 결과

검토·구현 기준: 2026-09-18

사용자가 제공한 cooperative-llm-mvp-spec-ko.md와 cooperative-llm-deep-research-ko.md를 설계 자료로 검토했습니다. 문서 안의 제안·예시 명령·향후 계획은 별도 실행 지시로 간주하지 않았습니다.

## 결론

두 문서의 기본 방향은 유지할 가치가 있습니다. 특히 task parallel과 model parallel을 구분하고, 승인 제공자 신뢰를 전제로 삼으며, 실행 완료와 결과 품질을 분리한 점이 적절합니다. 가장 큰 공백은 새로운 알고리즘보다 **동시성·권한·복구·회계의 실행 규칙을 코드로 확정하는 것**이었습니다.

이를 반영해 Relay라는 단일 운영자형 파일럿 서비스를 구현했습니다. 작업 화면, 영속 실행 코어, 원장, 제공자 프로그램, 출력 파일, 자체 호스팅 패키지를 포함합니다. 실물 GPU 추론과 성능 실측까지 완료한 상용 서비스는 아닙니다.

## 주요 한계와 적용한 개선

| 발견한 공백 | 적용한 개선 | 확인한 근거 |
|---|---|---|
| 결과·취소·lease 만료가 동시에 도착할 때의 우선순위 | 풀 revision을 조건으로 결과·정산·예약 해제를 원자적으로 확정. 충돌 시 최신 상태에서 다시 실행 | 중복 제출·동시 정산·취소 경쟁·CAS 테스트 |
| workflow 예산만으로는 여러 작업의 계정 잔액 중복 사용을 막지 못함 | 결제 계정별 가용 잔액과 작업의 확정액+예약액을 함께 검사 | 동시 예약 2개 중 잔액이 허용한 1개만 성공 |
| 작업 ID와 실행 시도를 혼동하면 늦은 결과가 새 결과를 덮어씀 | task, attempt ID, epoch, 서버 시각, hard stop 분리 | A 만료→B 배정→A 늦은 응답 거절 |
| heartbeat가 이전 실행을 갱신하면서 새 실행을 얻는 문제 | 갱신 요청과 새 할당 요청 분리. 만료된 갱신은 409 | stale heartbeat 테스트 |
| 토큰 자가보고로 정산할 경우 조작·토크나이저 구현 부담 | 문서 단위 고정 요율 10 CR. 사용량은 제한된 정수 필드로 기록하고 과금에 미사용 | 과대 usage 제출에도 요금 고정·비허용 필드 제거 |
| 실행 계약과 의미적 품질이 혼재 | 실행을 완료하면 정산, 원문 근거 검사는 별도 상태. 품질 재호출은 새 task와 예산 | 인용 실패→부분 결과→새 예약 테스트 |
| 제공자가 적립만 하고 다시 사용하지 못하면 경제 순환이 끊김 | 제공자 기여 계정을 다음 작업의 결제 계정으로 선택 | 기여 재사용 후 전체 크레딧 보존 |
| 출처 URL만으로는 문서 변경·인용 위치를 재현할 수 없음 | 원문 스냅샷, SHA-256, 정확한 인용 문자열, UTF-16 위치 저장 | 한글·이모지 원문 위치 검증 |
| “pause 완료”가 GPU 반환 완료와 같지 않음 | 서버 lease 철회 + 제공자가 소유한 llama-server 종료. 재개 전에는 모델 재적재 금지 | 프로세스 소유권·pause 반복 테스트; 실GPU 반환 시간은 미측정 |
| HTTP redirect·환경 상속에서 제공자 키가 누출될 수 있음 | redirect 거절, 추론 프로세스 최소 환경 변수, 키 해시 저장·폐기 | 실제 loopback redirect 실험·환경 검사 |
| IP 기준 제한이 동일 NAT의 정상 노드들을 차단할 수 있음 | IP 전체 제한과 노드별 제한 분리 | 지원 노드 수와 polling 주기의 산술 검토 |
| 출력 저장 한도에서 정산이 막힐 수 있음 | 최대 escape 출력과 품질 결과의 중복 저장을 고려해 단계당 64KB 여유 확보 | 정상 최대 escape 응답 정산 테스트 |
| 결과 정리 후 중복 영수증 응답이 깨질 수 있음 | 원문을 지워도 acceptedRawHash와 정산 영수증 유지 | archive→동일 결과 재제출 테스트 |
| 체험 화면을 실GPU 검증처럼 오해할 위험 | demo/live 상태·원장 분리, 모든 화면과 산출물에 실행 backend 표시 | API 및 브라우저 상태 확인 |

## 실제 구현 구조

- 사용자 화면: React 기반 한국어 웹 콘솔. 작업 제출, 문서 불러오기, 노드 회수·재개, 모델 승인, 제공자 키 발급·폐기, 원장, JSONL/CSV/Markdown 출력.
- 실행 코어: 플랫폼에 독립적인 JavaScript 상태 전이. 고정 map→validate→reduce 템플릿. reduce는 결정적 병합.
- hosted 저장: Cloudflare D1의 풀 상태 row + revision CAS.
- 자체 호스팅: Node HTTP 서버 + SQLite WAL. 동일 코어를 사용해 두 경로의 복구·정산 규칙을 일치시킴.
- 제공자: Python 표준 라이브러리. 로컬 llama-server를 전용 자식 프로세스로 소유. outbound poll/renew/submit/release. 원격 임의 명령·모델 다운로드 없음.
- 모델 계약: GGUF, 실행파일, chat template SHA-256과 고정 문맥. 파일 해시는 원격 계산 진위의 암호학적 증명이 아님.
- 보안: 단일 관리자 세션, CSRF 출처 확인, 제공자별 해시 인증키, 역할별 API, 요청 크기 제한, CSV 수식 방지, 원문/결과를 HTML로 실행하지 않음.

## 의도적으로 좁힌 부분

**상태를 하나의 풀 aggregate에 저장**했습니다. 초기에는 다중 테이블의 부분 정산과 outbox 복구 복잡도를 줄이고 한 원자적 변경으로 불변식을 검사하는 편이 적합하다고 판단했습니다. 이는 처리량을 위한 최종 구조가 아닙니다.

최대 20노드·8모델·미보관 24작업·작업당 4문서·4,000자·6필드·16논리 task·약 1.7MB 상태로 제한합니다. 상한은 화면·서버 양쪽에 반영했고 새 예약 시 향후 결과 공간을 검사합니다. 완료 이력·원장이 커지는 장기 운영은 관계형 테이블과 보관 저장소로 분리해야 합니다. D1의 row 제한과 단일 DB 직렬 처리 특성도 반영했습니다. [D1 공식 제한](https://developers.cloudflare.com/d1/platform/limits/)

스케줄링은 한 제공자에 승인 모델 하나를 고정해 모델 전환 비용 자체를 초기 범위에서 제거했습니다. 강제 적합성 조건과 작업 간 순환 배정을 사용합니다. 성능 예측·warm/cold 모델 전환·critical path 최적화의 우월성을 주장하지 않습니다.

참여자는 운영자가 승인한 제공자 키로 연결합니다. 운영자가 기여 계정을 대신 관리하는 파일럿이며 참여자별 웹 로그인·초대 메일·조직 RBAC·billing 시스템은 아직 없습니다.

## 검증 결과

| 검증 | 결과 | 범위 |
|---|---|---|
| 실행 코어 자동 테스트 | 28개 통과 | 복구·fencing·정산·예산·출처·기여 재사용·재시작 |
| HTTP 통합 검사 | 13개 통과 | 실제 Node/SQLite 서버의 인증·CSRF·제공자·동시 정산·재시작 |
| Python 제공자 테스트 | 8개 통과 | 구조화 요청·문맥·모델 해시·프로세스 회수·redirect·환경·pause |
| 브라우저 전체 흐름 | 통과 | 로그인→문서 3개→회수→재배치→완료→3종 다운로드→원장→새로고침 |
| 반응형 화면 | 통과 | 1440px 데스크톱과 390px 모바일, 모바일 메뉴, 가로 넘침 없음 |
| 브라우저 실행 오류 | 0건 | 해당 시나리오의 pageerror |
| TypeScript 검사 | 통과 | 화면·서버 라우트 |
| Worker / 자체 호스팅 화면 빌드 | 통과 | 배포용 출력 생성 |
| WebMCP | 구현 / 실행 검증 미실시 | 지원하는 브라우저 인터페이스를 사용할 수 없었음 |
| 실물 GPU / WAN benchmark | 미실시 | 장비·고정 모델·드라이버 제공 없음 |

제공자·HTTP 테스트의 inference 응답은 명시적인 synthetic fixture입니다. 실제 LLM 결과나 GPU 성능으로 제시하지 않습니다. llama.cpp 어댑터는 공식 서버 계약을 기준으로 작성했고, 사용할 고정 빌드에서 endpoint 지원 여부를 확인하도록 했습니다. [llama.cpp 공식 server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

## 실GPU 파일럿의 남은 인수 기준

1. 실물 Linux/NVIDIA 제공자 3대에서 같은 파일 해시의 모델로 문서 묶음을 끝까지 실행.
2. 실행 중 프로세스·네트워크를 끊어 완료 단계 보존, 미완료 호출 재배치, 중복 지급 0건 확인.
3. GPU 메모리 반환 시간과 소유자의 로컬 사용 영향 측정.
4. 블라인드 원문 대조로 인용·추출 의미 정확성 평가.
5. 같은 조건의 단일 노드 및 단순 배정 기준과 p50/p95, 전체 비용, 전력, 실패율 비교.
6. 서버 단독 만료 정리·백업 복원·장기 원장 보관·참여자 계정 권한 추가.

문서의 “20% 개선”, “95% 완료”는 그대로 **검증 목표**로 남겨 두었습니다. 구현 완료나 실측 성과로 바꾸어 표현하지 않았습니다.
