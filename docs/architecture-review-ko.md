# Relay 0.2: 아키텍처 검토와 구현 결과

검토·구현 기준: 2026-09-18

사용자가 제공한 `cooperative-llm-mvp-spec-ko.md`와 `cooperative-llm-deep-research-ko.md`를 설계 자료로 검토했습니다. 문서의 제안·예시 명령·향후 계획은 별도 실행 지시로 간주하지 않았습니다. 이후 요청에 따라 **지정한 중앙 서버가 스케줄링을 관리하고, LLM 추론은 참여자 개별 컴퓨터에서 실행하는 독립형 구조**로 정리했습니다. 결과물은 로컬 실행 패키지입니다.

## 구현 범위

두 기획서에서 task parallel과 model parallel을 구분하고 승인 제공자를 신뢰하며 실행 완료와 결과 품질을 분리한 방향을 유지했습니다. 가장 큰 공백은 새로운 알고리즘보다 동시성·권한·복구·회계의 실행 규칙이었습니다.

Relay는 이를 코드로 확정한 단일 운영자형 파일럿입니다. 한국어 작업 화면, 영속 실행 코어, 크레딧 원장, 제공자 프로그램, 결과 출력, 독립 실행 패키지를 포함합니다. 실물 GPU 성능이나 다중 사용자 상용 운영까지 검증한 서비스는 아닙니다.

## 주요 한계와 적용한 개선

| 발견한 공백 | 적용한 개선 | 확인 방법 |
|---|---|---|
| 호스팅·인증이 특정 서비스 플랫폼에 묶임 | Node.js + SQLite 중앙 서버, 자체 관리자 세션, 일반 HTTPS 제공자 프로토콜로 통일 | 별도 플랫폼 계정 없이 로컬 패키지 실행·빌드 |
| 브라우저가 사라지면 만료 처리가 멈춤 | 서버의 독립 유지보수 루프가 lease·기한 만료와 예약 해제를 처리 | 브라우저·HTTP 요청 없이 만료·재시작 복구 테스트 |
| 결과·취소·lease 만료가 동시에 도착 | 풀 revision을 조건으로 결과·정산·예약 해제를 원자적으로 확정 | 중복 결과·취소·유지보수 경쟁과 CAS 테스트 |
| 작업 예산만으로 여러 작업의 계정 잔액 중복 사용을 막지 못함 | 계정별 가용 잔액과 작업의 확정액+예약액 동시 검사 | 동시 예약 시 잔액이 허용하는 요청만 성공 |
| 작업과 실행 시도를 혼동해 늦은 결과가 새 결과를 덮어씀 | task, attempt ID, epoch, 서버 시각, hard stop 분리 | A 만료→B 배정→A 늦은 응답 거절 |
| 이전 실행 heartbeat가 새 실행까지 얻음 | 갱신과 신규 할당 요청 분리, 만료된 갱신은 409 | stale heartbeat 테스트 |
| 토큰 자가보고에 따른 정산 조작·구현 부담 | 문서당 고정 10 CR, 사용량은 제한된 정수로 기록하고 과금에 미사용 | 과대 usage에도 요금 고정·비허용 필드 제거 |
| 실행 계약과 의미적 품질이 혼재 | 실행 완료는 정산, 원문 근거는 별도 검사, 품질 재호출은 새 task·예산 | 인용 실패→부분 결과→새 예약 테스트 |
| 제공자가 적립한 기여를 재사용하지 못함 | 제공자 기여 계정을 다음 작업의 결제 계정으로 선택 | 기여 재사용 뒤 전체 크레딧 보존 |
| 출처 URL만으로 변경된 원문·인용을 재현하기 어려움 | 원문 스냅샷, SHA-256, 정확한 인용 문자열, UTF-16 위치 저장 | 한글·이모지 원문 위치 검증 |
| 회수 명령 수락과 실제 GPU 반환을 혼동 | 서버 lease 철회와 제공자 소유 llama-server 종료, 회수 상태에서 재적재 금지 | 프로세스 소유권·회수 반복 테스트; 실GPU 반환 시간은 미측정 |
| redirect·환경 상속으로 제공자 키 누출 가능 | redirect 거절, 추론 프로세스 최소 환경 변수, 키 해시 저장·폐기 | loopback redirect 실험·환경 검사 |
| 같은 NAT의 여러 노드가 IP 제한으로 차단됨 | IP 전체 제한과 노드별 제한 분리 | 지원 노드 수와 polling 주기 검토 |
| 출력 저장 한도 때문에 정산이 막힘 | escape 출력·검사 결과를 고려해 진행 중 결과마다 64KB 여유 확보 | 최대 escape 응답 정산 테스트 |
| 결과 보관 후 중복 영수증 응답이 깨짐 | 원문을 지워도 acceptedRawHash와 영수증 유지 | archive→동일 결과 재제출 테스트 |
| 체험을 실GPU 검증처럼 오해할 위험 | 체험/실제 상태·원장 분리, fixture 실행임을 표시 | API·화면의 실행 구분 확인 |

## 실행 위치와 데이터 흐름

| 구성 요소 | 역할 | 수행하지 않는 작업 |
|---|---|---|
| 지정 중앙 서버 | 웹 화면·관리자 인증, 승인 모델·노드·예산 관리, 작업 배정, lease·기한 처리, 인용 검증, 결과 병합, SQLite 저장·정산 | 모델 적재, LLM 추론 |
| 참여자 PC | 파일 해시 확인, 전용 llama-server 시작, outbound 작업 요청·갱신·결과 제출, 소유 프로세스 회수 | 다른 노드의 권한 행사, 원격 임의 명령 실행 |
| 운영자 브라우저 | 요청 제출, 상태 조회, 운영 명령, 결과 다운로드 | 주기적 스케줄링이나 만료 처리 |

1. 운영자가 문서 스냅샷·추출 필드·모델·예산·기한을 제출합니다.
2. 중앙 서버가 요청을 저장하고 결제 계정의 크레딧을 예약합니다.
3. 참여자 프로그램이 작업을 요청하면 서버가 승인 조건과 가용 슬롯에 맞춰 문서를 배정합니다.
4. 참여자 PC의 고정 모델이 추론하며, 프로그램은 해당 시도의 lease를 갱신합니다.
5. 중앙 서버가 제출 권한·시도·모델 계약을 검사한 뒤 실행 결과와 지급을 한 번만 확정합니다.
6. 정확한 원문 인용을 검사하고 검증된 필드를 결정적으로 병합합니다. 사용자는 결과를 JSONL·CSV·Markdown으로 내보냅니다.

중앙 서버에는 원문과 결과가 저장되고, 배정 문서는 참여자에게 전달됩니다. 중앙화한 범위는 작업 제어와 상태·검증·정산입니다. 모델 추론을 중앙 서버나 외부 LLM 서비스에 위임하지 않습니다. 제공자에 대한 별도의 inbound 연결도 필요하지 않습니다.

## 플랫폼 독립 실행

실행 경로를 React/Vite 화면과 Node HTTP/SQLite 서버로 통일했습니다. GPT 계정, Sites 인증, Cloudflare D1 바인딩, 플랫폼 전용 배포 도구는 실행·인증·저장의 전제 조건이 아닙니다. 외부 웹 서비스 게시나 소스코드 전송 없이 로컬 패키지로 전달합니다.

`npm run dev`는 중앙 서버 8788과 개발 화면 5173을 함께 실행합니다. `npm run build`는 화면 정적 파일을 만들고, `npm start`는 중앙 서버에서 화면과 API를 함께 제공합니다. 사전 빌드 ZIP은 Node.js만 있으면 `START-RELAY.cmd` 또는 `node standalone/server.mjs`로 실행할 수 있습니다.

원격 운영은 사용자가 선택한 서버와 도메인을 사용합니다. 기본 바인딩은 `127.0.0.1:8788`입니다. 같은 호스트의 TLS reverse proxy로 HTTPS를 종료하고 `RELAY_PUBLIC_ORIGIN=https://relay.example.org`, `RELAY_SECURE_COOKIE=1`을 설정합니다. 참여자는 `--coordinator https://relay.example.org --pool local-owner`로 접속합니다. 로컬 loopback 이외의 HTTP 주소는 제공자가 거절합니다. 원격 TLS 배포와 WAN 품질은 이번 로컬 검증에 포함되지 않습니다.

## 영속성과 스케줄링

상태를 하나의 풀 aggregate에 저장합니다. 결과 수락·원장·예약 해제를 하나의 revision CAS로 확정해 부분 정산을 피하고 모든 변경에 불변식을 검사합니다. SQLite WAL은 중앙 서버 로컬 디스크에 저장됩니다. CAS 충돌 시 최신 상태와 시각으로 최대 10번 재시도합니다.

`standalone/maintenance.mjs`의 서버 루프는 기본 1초 간격으로 만료된 lease·기한을 찾습니다. 변경이 필요한 상태에만 API와 동일한 전이·정산 코어를 적용합니다. 루프 중첩을 합치고, 종료 때 진행 중 작업을 기다리며, 저장 상태를 읽어 재시작 후 복구합니다. 체험도 브라우저를 닫은 상태에서 진행됩니다. 실제 작업 할당은 연결된 제공자의 요청에 응답해 수행하므로 서버가 존재하지 않는 제공자를 대신해 추론을 시작하지 않습니다.

스케줄링은 제공자마다 승인 모델 하나를 고정합니다. 모델 해시·런타임·템플릿·문맥·VRAM·허용 노드의 강제 조건을 적용하고 작업 사이에 순환 배정합니다. 노드당 활성 lease는 하나, lease는 30초, 한 시도의 hard stop은 180초입니다. 공급이 없으면 대기하며 작은 모델로 자동 교체하지 않습니다.

파일럿 상한은 20노드·8모델·미보관 24작업·작업당 4문서·문서당 4,000 UTF-16 문자·6필드·누적 16논리 task·약 1.7MB 풀 상태입니다. 저장 한도는 플랫폼 제한이 아니라 애플리케이션의 보수적인 운영 정책입니다. 완료 이력과 원장은 계속 쌓이므로 장기 운영에서는 관계형 테이블과 보관 저장소로 분리해야 합니다. 단일 풀 CAS가 처리량 한계와 충돌 지점이 된다는 점도 남아 있습니다.

서버 정지 중에는 새 배정·정산이 중단됩니다. 제공자는 lease를 갱신하지 못하면 소유한 추론 프로세스를 회수합니다. 단일 중앙 서버의 가용성을 보장하는 복제·자동 장애 전환은 구현하지 않았습니다.

## 권한·신뢰 모델과 범위

현재는 단일 운영자, 단일 풀, 승인된 제공자 키를 사용합니다. 운영자가 제공자별 기여 계정을 관리하고 대신 요청을 제출합니다. 참여자별 웹 로그인·초대 메일·자체 회원 가입·조직 RBAC·실화폐 billing은 아직 없습니다. “사용자 스케줄링”은 이러한 계정의 작업 배정과 예약·정산을 의미하며 다중 사용자 인증 서비스를 구현했다는 의미가 아닙니다.

관리자 세션, POST 출처 검사, 요청 크기·요청 빈도 제한, 노드별 키 해시, CSV 수식 방지, 원문·출력의 안전한 텍스트 표시를 적용했습니다. 추론 프로세스에는 제공자 키를 전달하지 않으며 모델과 런타임을 임의로 내려받거나 원격 명령을 실행하지 않습니다.

파일 해시는 승인된 파일 계약을 식별하지만 원격 계산이 정직하게 수행됐음을 증명하지 않습니다. 제공자 호스트는 배정된 원문을 볼 수 있습니다. 공개·비민감 문서와 승인 참여자를 전제로 합니다. 기밀 계산, 악의적 제공자에 대한 신뢰 없는 검증, 의미적 정답 보장은 범위 밖입니다.

## 화면 변경

사용자가 지정한 [Apple 디자인 스킬](https://github.com/dickwu/apple-design-skill)을 기반으로 작업 중심 화면의 계층·내비게이션·입력·상태 표현을 정리했습니다. 디자인 변경은 기존 작업 제출·노드 회수·모델 승인·원장·내보내기 기능을 보존하는 범위입니다. 별도의 플랫폼 로그인 선택지는 제거하고 중앙 서버의 관리자 인증을 사용합니다.

## 검증 범위와 재현 명령

```sh
node --test tests/engine.test.mjs tests/maintenance.test.mjs
node --test tests/http.test.mjs
python -m unittest discover -s tests -p "*_test.py" -v
npm run check
npm run build
```

| 검증 대상 | 확인하는 내용 |
|---|---|
| 실행 코어 | 복구·fencing·정산·예산 경쟁·출처·기여 재사용·영속 상태 |
| 서버 유지보수 | 브라우저 없는 만료·체험 진행, 동시 제출과 CAS, 유휴 상태 쓰기 방지, 중첩 처리·종료, 재시작 복구 |
| HTTP 통합 | 실제 Node/SQLite 서버의 인증·CSRF·제공자 권한·중복 지급 방지·재시작 |
| Python 제공자 | 구조화 요청·문맥·모델 해시·소유 프로세스 회수·redirect·환경 격리·회수 상태 |
| 화면 점검 | 로그인→문서 제출→회수→재배치→완료→출력→원장→새로고침, 작은 화면과 키보드 접근 |
| 타입·빌드 | 독립 React 화면 및 배포용 정적 파일 생성 |
| 실물 GPU·원격 WAN | 미실시 |

0.2 최종 검증에서 코어28개·서버 유지보수11개·HTTP13개 검사·Python8개가 통과했습니다. TypeScript·ESLint·Vite 빌드, 주요 브라우저 작업 흐름과 8개 상태의 Axe 접근성 검사도 통과했습니다. 세부 화면 기준은 [디자인 검토](design-review-ko.md)에 정리했습니다. HTTP·제공자 테스트의 추론 응답은 synthetic fixture이며 실제 LLM 결과나 GPU 성능으로 제시하지 않습니다. 어댑터는 [llama.cpp 공식 서버 계약](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)을 기준으로 작성했으며 운영에 사용할 고정 빌드에서 endpoint 지원을 확인해야 합니다.

## 실GPU 파일럿의 남은 인수 기준

1. 실물 제공자 3대에서 동일한 파일 해시의 모델로 문서 묶음을 끝까지 실행합니다.
2. 실행 중 프로세스·네트워크를 끊어 완료 단계 보존, 미완료 호출 재배치, 중복 지급 0건을 확인합니다.
